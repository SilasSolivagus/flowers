## 5 失效控制：47 条标准答案的核验

做法：对每个案例的标准答案文件，核对它在**索引真正读的那棵树**（`lsTreeEntries(HEAD)`）上还在不在。三种结果：

- `kept`：还在；
- `gone`：不在，也不是被索引过滤的——真删了；
- `filtered`：落在索引**故意排除**的目录/扩展名里（`dist/`、`node_modules/`、图片…）——不是今天才失效，而是一直对 C 不公平。

采用口径：**全部文件都不在了** → `invalidated`，不进分母。

## 7 判定与顾虑

**判定（一句话）：这次从 2 个仓扩到 216 个仓对定位既没帮助也没伤害，因为定位读的 `commit_history` 仍然只有 2 个仓 671 行；
用现有 harness 无法测出扩容的效果（unmeasurable），要测就得先补历史。**

顾虑，按重要性：

1. **扩容的收益没有落点。** 216 个仓里 214 个仓的合并历史是空的，`locateFromHistory` 对它们只能返回 `none`。
   索引（`blob_index`）扩了 216 个仓，但它服务的是 B 臂（评审用的静态索引），不是生产的定位路径。
   谁要把「扩到 216 个仓」当成定位改进，得先跑 `scripts/index-history.ts` 把那 214 个仓的历史补进库——
   那是几十分钟到几小时的 git 读取，且会改库（这一轮是只读测量，没做）。
2. **面一的标准答案比上一版大。** 4 条案例的答案并集从 8/7/27/27 变成 15/18/30/30，弱标准答案从 2 条变 4 条。
   结果是「排除弱标准答案」的子集从 5 条缩到 3 条（C 2/3），这个子集已经小到不该单独看。
3. **A 臂与 C′ 臂的检索式不可复刻。** `description` 列在库里不存在了，A/C′ 吃的是「标题 + context + problem + outcome」，
   文字不同、切出来的词不同。A 的唯一命中因此消失（0/7）。头条看 C（只喂标题，与线上口径一致），别拿 A 的 0/7 当回归。
4. **C 的候选可以指向已删文件。** #318 第 3 条 `capacity-card.vue` 已经不在 HEAD 上。候选来自历史路径、不校验存在性：
   好处是「这次改动可能删了这个文件」也能被看见，坏处是 PM 点开会 404。这一轮只记录，没改（改就是改生产行为）。
5. **面二仍然有泄漏**（查询就是答案那次合并的提交信息），绝对值 49%~51% 不能当「真实需求找得准」的估计，
   只能说明「检索没崩」。旧报告 §7 提过：面二应当作为回归闸门，任何改动 `history.ts` 的前后各跑 520 条。
6. **这套脚本没有单测接缝。** 文件末尾是 `await main()`，import 它就会跑评测，所以 `survivalOf` / `invalidation`
   只能靠跑输出核对（本报告的 §4.4 / §5 就是核对记录），没有 `vitest` 用例。要加用例得先把控制逻辑搬到 `src/` 下的纯模块。
7. **B 臂在旧抽屉上逐位复现，不代表索引没变。** `0f9a4d1`（903 字节的 `SvgIcon/index.vue` 让索引永不返回）确实改了
   索引器；只是这 40 条案例的命中没被它影响。索引器的回归应当用别的夹具盯。
