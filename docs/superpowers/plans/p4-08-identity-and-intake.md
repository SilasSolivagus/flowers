# P4-08 · 登录名换成邮箱 · 需求加「平台」· 旧描述拆六问

分支 `main`，起点 `8e783be`（P4-06 会话纪元收尾之后）。三件事共用一条迁移
`0013_p408_identity_and_platforms.sql`：两列都是**有历史行**的列，所以顺序都是
「先加可空 → 回填 → 再上约束」。

---

## 1. 一句话

登录凭证从 `members.name` 换成 `members.email`（`<拼音>@123pan.com`，来自企微通讯录），
**身份仍然是名字**；`requirements.platforms` 是一个 `text[]`，值来自一份八个键的固定
词表，参与指纹（于是所有老产物一起变旧，这是对的）；旧 Flower 的
`description` 可以被一个**一次性工具**拆成六问——六问里每一格都必须有原文引文，
引文逐字核对不上就丢掉那一格、并说清「这一格原文没写」。

## 2. 邮箱登录

### 2.1 换的是凭证，不是身份

| | 改之前 | 改之后 |
|---|---|---|
| 登录字段 | 姓名（`members.name`） | **邮箱**（`members.email`） |
| 唯一约束 | `members_name_unique` | **`members_email_unique`**（名字的唯一索引**保留**） |
| 登录返回 | `{ name }` | `{ name }`（**没变**） |
| 会话票据 | 装名字 | 装名字（**没变**） |
| `events.actor` | 名字 | 名字（**没变**） |
| `can()` / 通知扇出 | 名字 | 名字（**没变**） |

一句话：**下游一个字都没改**。改的只有两处——`src/core/auth/login.ts` 里
`memberByEmail` 取代 `memberByName`（并把限速的键从名字换成邮箱：去空白、折小写），
以及登录页/登录 action 的字段名 `email`。

「谁知道我是谁」仍然按 `members.name` 解析：`currentMember()` 读会话票据里的名字 →
`memberByName`；权限判断读 `requirementFacts`；通知按名字扇出；时间轴写的是名字。
所以这次改动**不会**让一条历史事件的 actor 变成一个邮箱。

### 2.2 没有给「按名字登录」留兜底

`attemptLogin(db, name, password)` 现在传一个名字进去会得到
`bad_credentials`（用例钉着：`凭证是邮箱：用名字登不进来`）。理由：

- 名字登录是一条绕过邮箱唯一性的旁路。公司口径是邮箱，留着它等于把「登录名」这件事
  又变回两个来源，而两个来源迟早不一致；
- 重名的两个人（真会撞）在名字登录下取决于 `order by id limit 1`，在邮箱下不可能撞。

### 2.3 MCP token：没有留、也不需要留名字兜底

MCP 的凭证是 token，不是登录名：请求 → `mcp_tokens.token_hash` → `member_id` →
`members.name`（`mcp/tokens.ts` 的 `identityFromToken`）。名字只是它反查出来的
`actor`，与「登录字段填邮箱还是姓名」毫无关系。**所以没有加任何按名字的解析口**。

### 2.4 失败口径没变

未知邮箱、密码错、账号已停用、账号没有口令——四条路共用 **`账号或密码不对`**
（`BAD_CREDENTIALS`），并且照旧跑一次 `burnDecoy` 的 scrypt 让延迟相同。
5 次失败锁 5 分钟的窗口现在按**邮箱**算（`lockedFor` 的键），用例新增了一条
「锁住一个人不影响另一个人」。

### 2.5 迁移怎么回填

```sql
add column email text;                       -- 先可空
update members set email = <企微通讯录的映射> where name in (...);   -- 七个人
update members set email = 'member-<id>@123pan.com' where email is null;  -- 其余（占位，唯一）
alter column email set not null;
create unique index members_email_unique on members (email);
```

这条迁移对**空库**与**有历史行的库**都成立（drizzle 生成的那一版直接
`add column ... not null`，在有行的库上会立刻失败——所以它被重写了）。

### 2.6 新的人怎么建

`createMember` 现在**必须**给邮箱：`邮箱不能为空（登录名是 <拼音>@123pan.com）` /
`邮箱格式不对（…）` / `这个邮箱已经有账号了（登录名必须唯一）`。只判「有 @、两边都不空、
没有空白」，**不写死域名**——域名是公司的规矩，不是这个系统的规矩。
设置 · 成员的列表里每人多一行邮箱（这一页是唯一能回答「这个人怎么登进来」的地方），
新增表单多一格 `邮箱`。

`scripts/seed.ts` 打印的初始口令表现在是 **名字 / 邮箱 / 角色 / 口令** 四列，因为要抄
下来的是**能登录的东西**。

## 3. 平台（`requirements.platforms`）

### 3.1 为什么是 `text[]` 而不是 jsonb

值来自一份**固定词表**、无序、去重、判等：`['h5','android']` 与 `['android','h5']`
是同一条需求的同一组平台。数组的 `=` 与 `@>` 就是这件事的原生语义；jsonb 会把「相等吗」
变成一次 JSON 归一，而这一列没有任何嵌套结构需要它。代价（不参与 `text` 的排序习惯）
在这张表上不存在。

词表**不在库里做 CHECK**：加一个平台（比如鸿蒙）不该是一次迁移。写入端按词表过滤
（`normalizePlatforms`：小写、去重、按词表顺序、丢掉认不出的键），读侧认不出的键原样保留
（不吞掉一条需求里的东西）。

| 键 | 中文 |
|---|---|
| `pc` | PC 客户端 |
| `web` | Web |
| `h5` | H5 |
| `ios` | iOS |
| `android` | Android |
| `api` | 开放接口 |
| `admin` | 运营后台 |
| `mini` | 小程序 |

空数组 = **未标注**（不是 null，也不是「不改」）。迁移里 `default '{}'::text[]`
把历史行一次性回填成空数组。

### 3.2 界面

- **录入 / 编辑表单**：八个 chips，多选。不用原生 `<select multiple>`：macOS 上那是一块
  暗色列表，「按住 ⌘ 点」是唯一的多选方式，没人会想到那是多选。`.chipbox` 是一个被
  样式化的 `<label>`，里面是**真的** checkbox（视觉藏起来、语义留着：键盘能用、读屏能读、
  `name="platforms"` 能提交）。一个都没勾 → 空数组 → 未标注。
- **抽屉「信息」段**：一行 `平台  H5 · Android`（空的时候是 `未标注`）。
- **看板卡上没有它，这是刻意的**。那张卡只有两行（标题 / 等谁），一个九列的板已经
  很挤；再塞一行标签会把「一眼看出这一段在等什么」挤掉。平台是「这条需求是什么」的
  分类，打开抽屉才需要它——而看板要回答的是「现在卡在哪」。
  用例把这条钉住：`getBoard` 的卡片上**没有** `platforms` 这个键。

### 3.3 指纹：加平台 → 所有老产物变旧（这是对的）

`FINGERPRINT_FIELDS` 从八格变成九格（`title`、六问、`prdUrl`、`platforms`）。平台的
序列化是 `normalizePlatforms(...).join(',')`：勾选顺序与重复不影响指纹，`null` 与 `[]` 同值。

**后果，明说**：数组长度变了，所以**每一个**历史 `input_hash` 都对不上，抽屉里每一份
老材料都会显示「需求已更新」。这不是 bug：那条记录的含义是「这份材料是照着一版**不含
平台**的描述生成的」，而现在描述里多了一格它会读的东西。想「老产物仍然新鲜」只有一条路
——序列化里跳过空平台——那等于「补了平台还说材料是新的」，正好是这条指纹要防的事。

改动落到的位置：`FINGERPRINT_FIELDS` / `FINGERPRINT_COLUMNS` / `FingerprintRow`，
以及四个生成入口各自的 `loadRequirement`（`compose` / `review`(复用 compose 的) /
`inspect` / `start`）与三个批次脚本的形状（`scripts/shape-corpus.ts`）。少抄一列的
表现是「那一列永远不参与指纹」，所以在类型上是 `platforms: string[] | null` 必填。

## 4. 旧描述 → 六问（`src/core/uemaster/intake.ts`）

```ts
splitDescription(cfg, { title, description }) → {
  context, problem, outcome, surfaces, edge_cases, out_of_scope, missing: string[], notes: string[]
}
```

### 4.1 它是**一次性工具 + 一个入口**，不是静默转换

owner 的裁决：不做保存时的自动转换。理由与「六问可空」同源——拆出来的是**猜测**，
猜错了要人看得见并改；静默转换会让一条老需求带着六段没人读过的文字，比空着更坏
（它看起来像有内容）。

- **界面**：编辑模式的六问旁边一个按钮「从原文拆六问」→ 一个 textarea 粘旧描述 →
  「拆分并填入」→ 六格被填进表单，**只填不保存**（保存仍然是下面那个按钮）。
  结果下面跟一张依据清单：填了几格、空的是哪几问（用产品里的标签）、每一格用了原文的
  哪一句。
- **CLI**：`npx tsx scripts/split-description.ts --file <path> [--dry-run]`，
  打印六问 + missing + notes + 计数。`--dry-run` 不调模型，只报字数、标题、模型配置
  在哪一层（**不打印 key**）。

### 4.2 三条硬规矩

1. **必须有据**：每一格都要能落回原文的一整句（`span`）。原文没写 → 那一格 `''`、
   列进 `missing`、**不编**。提示词里明写「不要推断、不要写『无』『暂无』『未提及』」。
2. **引文逐字核对**：`span` 与原文两边都走 `review.ts` 的 `normalizeQuote`
   （压掉空白含全角空格、去 markdown 强调符与引用符、去中英文标点引号、折小写），再判子串
   ——与评审那一关**同一套归一**。放宽的方向是**格式**不是内容：改词、改语序、拼接两处，
   归一之后一定对不上。核对失败 → 那一格内容丢掉、进 `missing`。
3. **依据要留痕**：`notes` 里两种记号——
   - `context ← 「原文的一整句」`：采用了（这条 `←` 的引文逐字在原文里，用例钉着）；
   - `surfaces ⨯ 「…」`：模型给了内容但引文在原文里找不到，**已丢弃**。

   所以「`missing` 但没有 `⨯`」= 原文根本没写；「`missing` 且有 `⨯`」= 模型编了、被拒。
   这两种空不是一回事，界面与报告都分开说。

### 4.3 失败口径

- 模型配置不全 / 接口报错 → `AppError('provider_error', 服务端原文)`；
- 回话里没有 JSON → `AppError('split_failed', '模型的回话里没有六问的 JSON…')`；
- **回话里六格全都对不上原文 → 不报错**：六格全空、`missing` 满六格、`notes` 六条 `⨯`。
  这比抛错有用（它说的是「这段原文真的没写这些」）。

### 4.4 一个实测出来的数字

`SPLIT_MAX_TOKENS` 一开始是 4096。第一次拿 PAN-6 那份 16,512 字的 PRD 真跑，
`deepseek-flash` 把 4096 全花在思考上（`reasoning_content` 12668 字、`content` 0 字），
`provider.complete` 回了一句「模型把输出预算用在了思考上」。改成 **16000** 之后一次通过
（59 秒）。这一条写进了代码注释——下一个改这个数字的人应该看到它为什么是 16000。

### 5.1 Run 1 · 正式 PRD（16,512 字）

```text
文件：tests/fixtures/prd-pan6.md
标题：prd-pan6.md
原文：16512 字
模型：platform 层 · deepseek-flash · 地址 https://api.deepseek.com/v1 · key 已配

── 六问（59087ms） ─────────────────────────────────────

✔ context（谁在什么情况下用）
  分享页访问者在 App/H5 的有效分享链接内，从根目录或任意子文件夹进入搜索，快速定位文件或文件夹并继续沿用原分享页操作。

✔ problem（现在怎么做 / 哪不好）
  App、H5 分享页的默认搜索范围需要统一为全链接搜索，并继续沿用一期已确定的搜索规则。

✔ outcome（做成什么样算成功）
  用户默认从整个分享中查找内容，在深层目录能识别当前位置并快速切换层级；App、H5 可完成移动端搜索、多选和原分享页操作。

✔ surfaces（涉及哪些页面 / 入口）
  App、H5 有效分享页工具栏的搜索入口，以及点击后进入的独立搜索页或独立搜索状态。

✔ edge_cases（失败 / 空 / 无权限怎么办）
  首批搜索失败时显示“搜索失败，请稍后重试”；无结果时提示“暂无搜索结果，换个关键词试试”且不写历史；加载更多失败保留已加载结果和选择并仅重试失败批次；目录无权限或失效时不跳转并沿用现有失败处理。

✔ out_of_scope（这次不做什么）
  本期不新增高级搜索、文件类型筛选、文件大小筛选、AI 搜索或跨分享链接搜索。

── 计数 ────────────────────────────────────────────────
filled:  6 / 6
missing: 0 格
notes:   6 条（采用 6 / 丢弃 0）

── 依据（notes） ───────────────────────────────────────
context ← 「在文件数量多、目录层级深的分享链接中，快速定位文件或文件夹，并继续使用原分享页操作。」
problem ← 「二期继续沿用这些规则，并将 App、H5 分享页的默认搜索范围统一为“全链接搜索”。」
outcome ← 「用户默认从整个分享中查找内容；在深层目录中能识别当前位置并快速切换层级。」
surfaces ← 「有效 App、H5 分享页的工具栏新增搜索入口；历史有效分享链接和新建分享链接使用同一规则。」
edge_cases ← 「首批失败：“搜索失败，请稍后重试”。」
out_of_scope ← 「新增高级搜索、文件类型筛选、文件大小筛选、AI 搜索、跨分享链接搜索。」
```

**计数**：filled **6/6** · missing **0** · rejected（`⨯`）**0**。

**读法**：材料全在的时候，六格都能落到一句原文上，一句都没被拒。三处值得注意：

- `edge_cases` 是最好的证据：它把四条分散在不同章节的异常（首批失败 / 无结果 /
  加载更多失败 / 目录无权限）合成了一段话，而引文只取了其中一句。**这是「value 不等于
  span」的正确形态**——value 是答案，span 是它站得住脚的那一处；多出来的三条来自原文
  其它位置，但每一格只要求「有一处支撑」。要么接受这个口径，要么把提示词改成「一格一句」；
  我选了前者，因为六问要的是**可用的一段话**，不是六条摘抄。
- `problem` 那一格其实偏「现状陈述」而不是「哪不好」：原文说的是「把默认范围统一为
  全链接」，那是本期的变化，不是痛点。模型把 02「需求背景」里那句当成了 problem。
  **这属于内容判断问题（口径松），不是事实问题**（引文真的在原文里）。
- `out_of_scope` 少了一条（「App、PC 主站搜索整体改版」在另一段），它只取了
  「新增高级搜索…」那一句。同样：不是造假，是**没取全**。人要在界面上补这一句。

1. **三格的引文是同一句话**（整段原文就是一句）。这不是巧合：工具的口径是「这一格

   这两件事），但如果人只想要一处，就得自己删——这正是「只填不保存」的理由。

## 8. 已知边界 / 这一轮没做

1. **平台不影响扇出**：通知与权限仍然只看负责人 / 条线 / 状态。一个平台值未来若要
   参与「按端派单」，那是另一个决定。
2. **抽屉的「信息」段多了一行**：九列看板 + 一行信息 = 这是这一轮唯一的界面密度
   变化。看板卡没动（刻意的，见 §3.2）。
3. **拆分器不改原文**：它只产出六问。旧 `description` 本身不落库——我们的库里没有
   那一列（六问就是描述）。要留原文，请把它贴在「这次不做什么」以外的地方或留在旧系统。
4. **`splitDescription` 的 `title` 只用于提示词**：它不进输出。所以 CLI 对没有 markdown
   标题的文件取文件名当标题——不影响拆分质量（原文才是依据），但报告里读起来会有点怪。
5. **限速计数仍在进程内存**（P4-04 的老边界）：多实例部署时阈值变成「5 × 实例数」。
   这一轮把键从名字换成邮箱，判断本身没改。
