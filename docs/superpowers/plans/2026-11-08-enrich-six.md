# 把旧描述拆进六问的空格（`scripts/enrich-six.ts`）

> 完成计划里的最后一项：`scripts/migrate-flower.ts` 把 Flower 的自由文本 `description`
> 搬进了 `context`，其余五格留空。这一步用「从原文拆六问」那个函数把原文拆开，
> **只填还空着的格**，把 626 条老需求从「一段话 + 五格 NULL」变成「六问有内容」。

分支 `main`，起点 `1491aa2`。

## 0. 结论先说

- 试跑 5 条：**有据（grounded）**，六格里的每一条 `←` 引文都能在原文里逐字找到，
  **丢弃 0 条**，没有编事实。质量可以跑全量。两类毛病记在 §2。
- 全量：**626 行**跑完，`problem` 445 行、`outcome` 526 行、`surfaces` 374 行、
  `edge_cases` 102 行、`out_of_scope` 67 行；`problem` 与 `outcome` 同时为空的从
  **626 → 25**。
- 代价：三次跑（全量 + 两轮失败重试）合计 **51.1 分钟**模型时间；**1 行**（`#794`）
  反复超时没补上，其余失败都重试成功。
- 815 行 / 803 条 `legacy_ref` 前后不变；`context` 一个字没动；没有写过一个空串。
- 一条附带结论：旧文本里**几乎不存在第五、六问**——补完之后 `edge_cases` 只有 16%、
  `out_of_scope` 只有 11% 的行有内容。这不是工具没跑，是原文就没写（§4）。

## 1. 脚本与参数

```
npx tsx scripts/enrich-six.ts --limit 5 --dry-run     # 试跑：调模型、全打印、不写库
npx tsx scripts/enrich-six.ts --only 1234             # 只补这一条（失败行重跑用）
npx tsx scripts/enrich-six.ts --limit 20              # 只取前 20 条（按 number 升序）
npx tsx scripts/enrich-six.ts --concurrency 8         # 并发（默认 4）
npx tsx scripts/enrich-six.ts --only-file retry.txt   # 只补清单里的编号（失败重跑）
npx tsx scripts/enrich-six.ts                         # 剩下的全跑
```

| 参数 | 默认 | 作用 |
|---|---|---|
| `--limit N` | 不设 | 只取 N 行。按 `number` 升序，所以「先跑 5 条看看」是稳定的前 5 条 |
| `--only N` | 不设 | 只处理 `number = N` 这一条；不在范围内时明说为什么不在 |
| `--only-file <path>` | 不设 | 只处理清单里的编号（一行一个）。**失败重跑就靠它**：把日志里 `失败：` 那几行的 `#数字` 抄成一份清单 |
| `--concurrency N` | 4 | 并发宽度（固定宽度并发池，见 §6） |
| `--dry-run` | 关 | **照常调模型**，把六格与依据全打印出来，但一行都不写库 |

**`--dry-run` 与 `split-description.ts` 的同名参数不是一回事**：那个脚本的 `--dry-run`
是「不调模型，只看提示词撑不撑」；这里的 `--dry-run` 是「试跑判质量」——它必须真的
去问模型，否则没法判「填进去的到底有没有据」。代价是它照样花钱，所以默认关。

选行口径只有一个（`NEEDS_WORK`，脚本里是常量）：

```sql
legacy_ref is not null
and context is not null
and (problem is null or outcome is null or surfaces is null
     or edge_cases is null or out_of_scope is null)
```

「有一个空格就选」而不是「五格全空才选」：这管子随时可能被跑第二遍、第三遍，而第二遍
遇到的行大多已经填了两三格了。

### owner 的裁决怎么落成代码：只填空格，不覆盖已有内容

**一格已经有字，就一个字都不动。** 理由写在脚本头注释里：那段原文是提出需求的人当年
写的，模型给的是对它的猜测；`context` 那一列是原文的唯一一份副本，写坏了没有第二份可以
恢复。这条规矩落成**两道锁**：

1. `planWrites()`：只把「内存里是 NULL」且「模型给了非空内容」的格放进 UPDATE 参数。
   已经有字的格根本不出现在 SQL 里。
2. `writeRow()` 的 SQL 自己再兜一道：

   ```sql
   update requirements set
     problem = coalesce(problem, $1), outcome = coalesce(outcome, $2), …
    where id = $id and (problem is null or …)
   ```

   哪怕这份行数据是几分钟前读的、中途有人（或另一个实例）已经填过，这条 UPDATE 也
   碰不到它——命中 0 行时脚本打一行「跳过：要写的那几格已经被填过了」。

**模型这一格没话说，就不写**：`''` 直接跳过，NULL 保持 NULL。不拿空串去覆盖「没有」——
库里必须还能区分「模型没说」与「这里写了一个空值」。

### 断点续跑

进度**只存在库里**：每条写完立刻提交（这一行的几格在同一个事务里），没有进度文件、
没有 seen 集合——那种东西第二天就会与库对不上。崩了重跑，选行条件自然把已经补完的
排除掉。跑完打印「失败 N 行 + 编号」，把那几行的 `#数字` 抄成一份清单喂给
`--only-file retry.txt` 就只补它们（§3 的两轮重试就是这么跑的）。

### 一行失败不拖垮整批

模型那一步抛了（超时 / 回话里没有 JSON / 接口报错）或者库写不进去：记一行、**那一行
原样不动**（写库在事务里，失败即回滚）、接着跑下一条。**脚本内部不做自动重试**：
自动重试会把「这条一直失败」藏进日志的中间，而「跑完的失败清单 + 一次显式的
`--only-file` 重试」是看得见的重试，剩下没救回来的才有资格写进报告。

### 我的判断：**有据，可以跑全量**

判「有据」的证据不是读起来像不像，而是三件可核对的事：

1. **0 条引文被丢**。5 条共 18 条 `←`，没有一条 `⨯`。也就是说模型给的每一格都能在原文
   里逐字找到（`quoteInPrd` 那关没拦下任何东西）——它没有为了填满而编。
2. **没有凭空出现的具体事实**。最容易被编的是「失败怎么办」：5 条里 4 条 `edge_cases`
   是空的，只有 #21 给了内容，而那一格的内容（「某一域名被封禁时…」）确实是原文说的那
   件事。六格里没有出现「失败时提示重试」「需要登录」「限流」这类原文里没有的话。
3. **留空留得住**。`out_of_scope` 5 条全空——原文里没有一条说了「这次不做什么」。
   这是最容易被模型硬凑的一格（「本次不涉及其他端」），它没有凑。

两类毛病，都记在这里，但它们不构成「停止」的理由：

- **单句原文会把同一句摊到好几格。** #21 的原文只有一句，于是五格共用同一个 span，
  `edge_cases` 那一格的内容其实是「问题」的复述，不是「失败/空/无权限怎么办」。
  #19 的 `outcome` 也是把请求（「优化 X 以减少压力」）复述成验收标准，而原文并没有
  给验收口径。**这是「原文太薄」的必然结果，不是模型在编**：一句话里确实没有第五问
  的答案，模型选择了复述而不是留空。下游看到的是一句真话，只是信息量低。
- **#18 的 `problem` 是把「需要什么能力」当成了痛点。** 原文那段话本来就没有区分
  「现状」与「要做成什么」，模型按句子切了一刀。同样是复述而非编造。

判断的分界线是「它有没有说原文没说过的事」，而不是「这六格是不是都很饱满」。前者它
守住了，后者材料本身给不了。所以：**跑全量**。也正因为这两类毛病，报告最后（§4）单独
列了「仍然缺格的行」——那才是这套工具诚实的地方。

## 4. 仍然缺格的行，以及为什么

补完之后 626 行里 **15 行五格全满**，**611 行仍缺至少一格**。缺在哪：

| 格 | 仍为空的行 |
|---|---:|
| `edge_cases` | 524（84%） |
| `out_of_scope` | 559（89%） |
| `surfaces` | 252（40%） |
| `problem` | 181（29%） |
| `outcome` | 100（16%） |

原因只有两类，都不是「工具没跑到」：

1. **原文里就没有这一问的答案（绝大多数）。** 这是「必须有逐字引文」那条规矩在起
   作用：模型想不出来就只能留空。典型是 21 行五格全空的需求，原文本身就是一句
   备注或一个链接：

   | # | 原文 | 结果 |
   |---:|---|---|
   | 29 | `技改需求` | 五格全空 |
   | 400 | `第二期` | 五格全空 |
   | 262 | `由文件多选拆出的需求` | 五格全空 |
   | 585 / 598 / 634 | `https://doc.weixin.qq.com/doc/…`（只有链接） | 五格全空 |
   | 210 | `根据 2026-03-30 截图补录，当前已进入设计中阶段。` | 五格全空 |

   同一类里也有「薄一点、刚好够一句」的：`web分享页背景广告更新SDK`（15 字）只填上了
   `surfaces`（「分享页」），其余四格空；同一长度的 `APP端文件面包屑接口性能优化`
   则一格都没填出来——同样是 15 字，能不能拆出东西取决于里面有没有「谁/什么页面/
   要达成什么」这些词。

2. **`#794` 反复超时（1 行）。** 见 §3。它的原文 658 字，值得单独重跑一次——但
   `splitDescription` 的超时是共用常量（界面上那个按钮也是 60 秒），改它属于另一件事，
   所以留着并写在这里。

**这就是「诚实」的样子**：611 行仍然缺格，但缺的每一格都能说清是哪一问原文没写。
反过来看，`edge_cases` 只有 16%、`out_of_scope` 只有 11% 能填上，本身是一条产品结论：
**这 626 条老需求的自由文本里，当年几乎没有人写「失败怎么办」和「这次不做什么」**。
下游生成材料时就在这两处猜——这是原文的缺口，不是这次拆分的缺口。

## 6. 并发与耗时（为什么是 8）

先量了三次再定：

| 试验 | 行数 | 并发 | 墙上时间 | 失败 |
|---|---|---|---|---|
| 试跑 | 5 | 4 | 37.5s | 0 |
| 探针 | 8 | 8 | 34.7s | 0 |
| 探针 | 16 | 16 | 60.0s | 1（`请求超时：60 秒内没有响应`） |
| 全量 | 626 | 8 | 36.8 分钟 | 43（6.9%，全为 60s 超时） |

单条延迟在 6–55 秒之间（`deepseek-flash` 是推理模型，`splitDescription` 给了 16k 输出
预算与 60 秒超时，思考本身就吃掉大半）。16 路并发时出现第一条 60 秒超时，说明再加宽就是
拿失败率换速度，于是全量固定用 **8**。事后看 8 路也有 6.9% 的超时（43/626），而把并发
降到 1 重试那 9 行时它们仍然慢（均 44 秒/行）——**超时来自个别输入的思考长度，不是并发
挤出来的**。真要降失败率，得从 `splitDescription` 的超时或输出预算下手，那属于另一件事。

并发池是**固定宽度、抢同一个游标**（`runPool`），不是 `Promise.all(items.map(...))`：
后者会把 626 个请求一次甩出去，网关限流、连接池也会被打满。

## 8. 备注与遗留

- **626 而不是 625。** 任务书写 625 条有 `context`，库里现在是 **626** 条
  （`legacy_ref is not null and context is not null`）。差的那一条不影响口径：选行与
  计数都按实际条件算，脚本开头打印的就是 626。可能是任务书写下之后又补搬了一条。
- **`context` 没有被改写。** 六问里 `context` 也回了一份，但脚本从头到尾没把它放进
  UPDATE 语句——选行条件保证它已经非空，而它一个字都不许动。
- **没有写事件。** 这次只改六列，没往 `events` 里写 `requirement.enriched` 之类的东西：
  任务是「填空格」，事件表留给有下游消费者的事件。要追溯可以看 git 与这份报告。
- **不碰的东西**：`src/core/locate/*`、数据守卫（`src/db/reset.ts` 那几条）、任何迁移。
- **失败行怎么重跑**：跑完的清单里有编号，`--only <number>` 逐条，或直接再跑一遍整条
  命令（选行条件会自动只取还有空格的行）。
