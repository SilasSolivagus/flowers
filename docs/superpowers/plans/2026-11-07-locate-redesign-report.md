## 0. 量了什么、怎么量的

### 0.1 三个臂

| 臂 | 是什么 | 在生产里的位置 |
|---|---|---|
| **A** | 冻结的老办法：`ssh grep` + **26 条**中英词表 + 30 条停用词 + **一份自带的 `keywordsFrom` 副本**（`pathA`，见下面的「A 臂怎么冻结的」） | 重做前线上那条 |
| **B** | 静态索引 `locateAcross`（路由/导入/符号） | 现在只给**评审**用；走查不用 |
| **C** | **新生产路径**：`commit_history` → `locateFromHistory`（中文提交信息检索 → 前 5 次合并 → 文件聚合） | 走查的**唯一**一路（`inspect.ts`） |
| **C′** | 与 C 同一份实现，喂 A/B 那句「标题 + 描述」 | 不是生产路径，只用来量「检索式」这一项的贡献 |

C′ 存在的理由：C 的检索式是**只有需求标题**（`locateQuery`，见 `inspect.ts` 的 `queryOfRequirement`），
A/B 的检索式是「标题 + 描述」。若只报 C 而 C 恰好更好，就没法排除「它赢在拿到了一句更短的话」。
两条都报：**C 是线上口径，C′ 是同口径对照**，两者差值 = 检索式贡献，不是实现差异。

**A 臂怎么冻结的（终审 Blocker 3）。** 决赛前的这一版报告的 A 臂**没有真冻结**：bench 里的
中英词表是 **31 条**，而 `scripts/compare-locate.ts` 的冻结版是 **26 条**——多出来的
权益 / 空间 / 域名 / 实况图 / 风控 正是 7 条案例标题里的词；而且它 `import` 了**生产**的
`keywordsFrom`，而虚词过滤是本分支 `5d818ce` 才加的。于是「A 1/7 → C 5/7」这个差值里混着
「A 拿到的词表更好」和「A 用的抽取器是新的」两件事，不是干净的改前/改后。

现在 `scripts/bench-locate.ts` 里的 A 是**冻结副本**：26 条词表、30 条停用词、以及一份
**不依赖生产代码**的 `keywordsFrom`（语义取 `5d818ce` 之前——**无虚词过滤**），打分口径也照
`compare-locate.ts` 的冻结版（路径命中 ×10 + 正文命中、只留路径命中过的文件、每仓 6 个）。
**A 臂与本分支代码零共享**：`import` 生产实现等于让尺子跟着被测对象一起变形，而这条评测
的全部意义就是那个差值。§6 的第 1 张表是重测后的数字。

### 0.4 数据与耗时

```
镜像合并：uni-app 85 条 / pc 173 条 · 需求库 803 条
commit_history（C 的语料）：657 行（123pan-pc 533 + 123pan-uni-app 124）
```

复现（本机，2026-11-07）：

```bash
npx tsx scripts/bench-locate.ts --surface 1 --verbose --json /tmp/bench-1.json   # 面一 7 条，三臂，约 2 分 36 秒
npx tsx scripts/bench-locate.ts --surface 2 --commits 40 --json /tmp/bench-2-40.json  # 面二 40 条三臂，约 21 分钟
npx tsx scripts/bench-locate.ts --surface 2 --c-only --json /tmp/bench-2-all.json     # 面二 513 条只跑 C/C'，约 40 秒
```

A 一条要 30 秒上下（每条查询在两仓各做一遍 `lsTree`，再对每个关键词各打一次 `ssh grep`），
所以面二的「三臂同案」只能做 40 条；C 是纯函数，513 条全跑了。**两个分母分开写，不混。**

重建数据之后（`bash /tmp/restore-demo.sh` + `tsx scripts/index-history.ts --repo 123pan-pc --repo 123pan-uni-app`
把表补回 657 行）我又跑了一遍 `--surface 1 --c-only`：7 条的排名与三档分布**逐条相同**，
噪音仍是 20。`locateFromHistory` 是纯函数，这是它该有的样子；不同就是 bug。

### 0.5 口径差别（必须先说，否则表会读错）

bench 里 C 的语料是**两仓并集**（657 行），因为 A/B 也是两仓口径。生产上 `inspect` 是**按单仓**检索的
（`input.repoId`）。我对 7 条逐条测了单仓口径，结果见 §2 最后一列：**并集并不总是更好**——
#797 在并集里掉到第 6，只搜 uni-app 反而是第 1（pc 的 `Share*` 组件把它挤下去了）。
所以表里的 C 是一个**既不更严也不更松、但确实不同于线上**的口径。

## 3. 这次重做到底改变了什么（给 PM 看的一段）

### 3.1 材料里现在只会出现四种句子，且四选一，不合并

代码在 `src/core/locate/copy.ts`，全仓只此一份；**这一段由代码写进产物顶部的横幅**
（`src/core/locate/banner.ts`），模型在正文里提没提它都不影响它出现（终审 Blocker 2）。

**① 代码本身没读到**（镜像连不上/仓没配，`absent`）

> 代码没读到，这一轮不含任何现状判断。（原因：镜像连不上）请与研发确认现在实际是怎么做的，
> 确认后更新 PRD 文档，材料会标记为旧版并重新生成。

**② 代码读到了，但合并历史/库没读到**（也是 `absent`，措辞分开）

> 代码读到了，但合并历史没读到，因此这一轮不含现状判断。（原因：读 commit_history 失败……）
> 请与研发确认……

**③ 读到了，但没找到**（`none`）

> 没能在代码里定位到这条需求的实现。请与研发确认现在实际是怎么做的，确认后更新 PRD 文档……

**④ 有候选，但不确定**（`candidates`，第一版**一律** `low`）

> 最可能的位置（**待研发确认**）：
> 1. `src/pages/video/video.vue` ← 出自 11-03「用户权益缩减」
> 2. …
>
> 以上是线索，不是结论。请与研发确认……

四句的措辞是**互相不共用关键词**的（`ABSENT_HEADLINE` / `ABSENT_HISTORY_HEADLINE` /
`NOT_FOUND_HEADLINE` / `LOW_CONFIDENCE_HEADLINE`），理由不是文风：一旦两句开始接近，迟早并成
一句，PM 就再也分不清「没看到代码」和「看到了但没有」——这几个要的动作完全相反（催运维接镜像 /
查历史库 / 去更新 PRD）。

**①②原来是一句**（「一个都没找到，或代码没读到」）。终审 Blocker 1 用一个真实事故把它拆开了：
「两仓的合并历史都读失败」这条路径上 HEAD / lsTree / repoShape **都已经读到了**，却抛出了
「代码没读到」，PM 因此去催镜像（该查的是历史库），而且那份本来能出的材料整份消失。现在
这条路径**照样出材料**（`inspect.ts` 里有一段注释写明三条兜底），横幅第一句就是 ②，`why`
原样带出。

### 3.2 与「重做之前」的差别（这是量出来的，不是说的）

重做前（**冻结后的** A 臂）在 7 条上：**4 条直接空手（`none`）**，另外 3 条交了 4 / 5 / 6 个文件
（共 15 个），**只有 1 条答案真的在里面，而且排第 4**。也就是说材料要么说「没找到」，要么给一份
看着有答案、其实只有 1 条沾边的清单——PM 无法从材料本身分辨哪条是蒙的。

重做后（C 臂）：**7 条里 6 条命中、1 条落 `low`、0 条落 `none`**，而且每条候选都自带
「出自哪天哪次合并」——PM 可以自己去 git 里核对这句话，这是我们能给的最硬的线索。

**一处必须自己纠正的旧结论**：上一版写「清单变短了，错的也少了（噪音 30 → 20）」。A 冻结之后
噪音是 **14**，C 是 **20**——**C 的清单比 A 的更吵**。原因是结构性的：C 固定交最多 6 条、每条都带
出处，A 交不出来时就交空。所以这条重做换来的不是「更干净」，是「有出处的 6 条 vs 空手/蒙的 3 条」；
噪音这个指标在两种清单形态之间本来就不可比（A 的 14 是 3 条清单的总和，C 的 20 是 7 条的总和，
分母不同）。这句话上一版是错的，改在这里，不改数字。

**必须说清的一点**：这次 7 条**没有一条落到 ① 或 ②**（两者都是 `absent`：代码没读到 / 历史没读到）。也就是说「该说不知道的时候说不说」这件事，
本次**没有真实数据**验证，只有单测（`copy.ts` 的常量、`locate-history.test.ts` 里「历史里没有 → 返回 `none`」）
和类型（`LocateResult` 三支联合）在兜。见 §5。

### 3.3 三条已知代价

1. **同一次合并的并列把真答案卡在第 5/6 位。** 一次合并动的所有文件权重完全一样，聚合时按路径升序取前 6。
   #782（动 10 个文件）答案被挤出清单；#797（动 82 个文件）答案落在第 6。
   也就是说：**合并动得越宽，真答案越容易被自己的队友挤掉**。
2. **需求标题用词与提交信息完全不同 → 必然 `none`。** 提交信息平均 20~40 字、口语、带 `feat:`；
   需求标题是 PRD 体。二者一个二字组都不重合时，`locateFromHistory` 返回 `{ kind: 'none' }`，
   材料走句 ③（「读到了、没找到」）。本次两个面都没出现（面一 0 条、面二 0 条），所以这条风险的**频率仍是未知数**——
   面二不存在这个问题（查询就是提交信息本身），面一只 7 条，且这 7 条都是热门功能。
3. **`absentRule` 只是提示词禁令，没有机器校验。** 它写在提示词里（「没读到的仓不要下任何现状判断」），
   但模型是否真的照做，代码**不核对**。与「路径拿 ls-tree 逐个核对」那条不同：那条写了就会被退回重答，
   这条没有对应的核对器。所以材料里仍可能出现越界的肯定句，而我们这次量的是检索，不是模型输出。

## 4. 下一步该做什么

### 4.1 把评测集从 7 条扩到 30 条（用 git 历史自动配对，人只做确认）

人工从零找「这条需求对应哪次合并」是这件事唯一的瓶颈，也是 7 条这个数字一直上不去的原因。
把「找」自动化、把「确认」留给人，是唯一走得通的路。具体做法：

**第 1 步：从镜像导出全部「候选标题」**（不新依赖，沿用 `mergeHistory` 的取法）

```bash
# 每条合并：sha / 分支 / 日期 / 这条分支自己的提交信息（去掉合并提交本身）
cd /srv/123pan-mirror/<repo>.git && git rev-list --merges HEAD | while read m; do
  b=$(git log -1 --format=%s $m | sed -n 's/.*from \([^ ]*\).*/\1/p')
  d=$(git log -1 --format=%cI --date=iso $m)
  msg=$(git log --no-merges --format=%s $m^1..$m | tr '\n' ' ')
  f=$(git diff --name-only $m^1 $m | grep -E '\.(tsx?|jsx?|vue)$' | tr '\n' ' ')
  echo "$m|$b|$d|$msg|$f"
done
```

**第 2 步：机器把「需求标题」和「候选标题」配起来**（打分用 `history.ts` 同一个公式，不另写一套）

对每条 `requirements.title` 取二字组集合，对每条合并的 `msg` 取二字组集合，算
`命中二字组 IDF 之和 ÷ 查询二字组 IDF 之和`（与 `rankMerges` 完全同一套），并且加一条时间窗：
`merge.merged_at` 落在 `requirement.created_at` 前 90 天之内（功能合进主干之后 PM 才立项，
所以方向是「合并早于需求」，不是反过来）。每需求取分数前 3 的合并作为**候选配对**。

**第 3 步：人只回答「对/不对/太宽」**

脚本吐一张表（`scripts/pair-cases.ts` 要新写，约 100 行，读数逻辑全部复用 `history-store.ts`）：

```
需求号 | 需求标题 | 候选合并 sha | 分支 | 提交信息 | 重合二字组 | 答案文件数 | 判定(__)
```

人只填最后一列。判定为「对」的进 `CASES`，并**必须**把「重合了哪几个词」抄进 `why` 字段——
现在 `CASES` 里那条「不写理由的配对不许进这张表」的规矩要原样保留，否则半年后没人敢信这些数字。
判定为「太宽」（答案文件数 > 10，或明显是多条分支的并集）的，单独打标，不进头条。

**第 4 步：验收条件（30 条这个数字要有内容，不是凑数）**

- ≥ 30 条判定为「对」的配对；
- 其中答案文件数 ≤ 10 的占 ≥ 80%（否则弱答案会把命中率抬高，见 #758/#788）；
- 覆盖两个仓、≥ 8 条不同分支（现在 7 条只覆盖 5 条分支，`userEquity` 一条被两条需求共用）；
- **一条需求只许配一条分支**（#782/#775 共用的那种要在配对阶段就拆开或淘汰）；
- 两条独立重跑，逐案排名必须完全一致（`locateFromHistory` 是纯函数，不一致就是排序不是全序，
  那是 bug 不是波动）。

### 4.2 什么时候才允许定准确率门槛

现在不允许——spec §9 写的是「第一版不设数字」，本次测量不改变这个判断。允许定门槛需要**三样东西同时成立**：

1. **数据**：§4.1 的 30 条满足上述四条验收条件，且弱答案占比 ≤ 20%。
2. **统计**：用二项分布的 Wilson 95% 下界，而不是点估计。以 30 条为例，第 1 名命中 18 条时
   点估计是 60%、下界约 **42%**；要下界 ≥ 50%，30 条里至少要有 21 条第 1 名。
   **只要下界不到门槛，材料里就只能写「线索」，不能升 `high`、不能对 PM 报任何百分比。**
3. **现场数据**：`locate_runs` 里至少有 30 条 `hit` 被人工回填过（`hit` 现在是 `null`，刻意不填——
   「还没评」不能被算成「评错了」）。bench 的标准答案来自 git，现场数据来自研发确认，两者必须能对上：
   若 bench 说 60% 而现场只有 20%，那说明「合并历史里能找到」不等于「PM 认得出这是我们说的那个功能」，
   这时该改的是输出口径，不是检索。

另外，面二应当作为**回归闸门**而不是准确率：任何改动 `history.ts` 的前后各跑 513 条，
第 1 名掉超过 15 个百分点、或 `none` 档从 0 涨到 5% 以上，就直接回滚——它抓的就是这种崩塌。

### 7.4 没做到的（本节新增）

1. **`detail` 只有走查那一轮填**：评审一轮本来就是一个合起来的结论（两个仓都读不到才算
   `absent`），没有分仓事实可写，所以评审行是 `detail = null`。统计脚本必须把 null 单独一档，
   不许当「两仓全见」处理——这条写进了列注释，但没有测试能钉住别人的 SQL。
2. **`detail` 没有约束**：形状靠写入方自觉（`Record<repo,{kind,why?}>`），库里没 CHECK。
3. 台账口径的「半盲」判定只验证过「一仓 absent + 一仓 candidates」这一种组合。
