# flowers v1 范围（上线第一版）

> 决定者：房超（owner）。写下这份是为了让"上线"有明确边界——**v1 只承诺一条链，其余全部标注为暂未开放。**

## 一、v1 承诺的唯一链路

```
需求进「收集」
   ↓  点「评估」
生成标准 uemaster 三栏材料：
   左   流程节点（来自六问；有页面的落在页面，没有页面的画逻辑时序）
   中   该节点的页面结构 / 逻辑时序图
   右   两栏标注：待需求方确认 · 待研发确认
```

**这条链之前的所有条件都已具备**：六问拆解、页面清单、时序图渲染、三栏装配、禁词自检。

## 二、v1 明确不做

| 能力 | 处理 |
|---|---|
| 评审材料（PRD 对照） | **代码保留，入口关闭**（feature flag），下一版开 |
| 走查材料（代码定位） | **代码保留，入口关闭** |
| 排期 / 开发 / 测试 / 上线 / 时钟推进 | 状态保留，不作为 v1 承诺 |
| 导出企微表格 | 入口保留但标「v1 暂未开放」 |
| 代码索引（216 个仓） | **不在 v1 链路上**——评估不读代码，v1 可完全不带 |

## 三、存量数据的处理（owner 裁决）

**C 方案：全部照常显示，每个非收集状态标一行「v1 暂未开放」。**

- 理由：藏起来会让人以为数据丢了。
- 想用新能力的人：**新建一条需求**（旧的那条删掉也行）——不做状态迁移、不做批量重置。

## 四、三条硬约束（v1 也必须守）

1. **推演的时序图必须标**：`逻辑时序（推演）· 待研发确认` + 一句「参与者与步骤按需求描述推的，代码里怎么实现要研发确认」。
   理由：v1 不读代码，那张图是推的。不标就是拿假时序图去评审。
2. **两栏标注不能合并**：待需求方确认 / 待研发确认——责任人不同，合并就没人认领。
3. **三句话纪律照旧**：读不到 / 没找到 / 待确认，永不合并。v1 不读代码，所以评估材料里**不出现任何"代码里如何"的断言**。

## 五、v1 的验收（可量）

```
[ ] 收集阶段的一条真需求 → 点评估 → 出三栏材料（含时序图与两栏标注）
[ ] 材料正文 0 处研发语言（机器检查有数）
[ ] 非收集状态的需求：看板可见，且明确标注「v1 暂未开放」
[ ] 评审/走查入口关闭后，没有死按钮、没有 500
[ ] 204 份历史材料不受影响（静态 HTML）
```
