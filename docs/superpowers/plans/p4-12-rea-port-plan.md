# 把 REA 的思路移植到「查我们自己的代码仓库」

> REA（[morluto/rea](https://github.com/morluto/rea)，Reverse Engineer Anything）解决的是
> **没有源码**时怎么读懂一个软件。我们有一整套 git 镜像，所以它的**主体能力用不上**：
> 反编译、Ghidra/Hopper/IDA provider、进程捕获、ADB、固件解包——这些一律不移植。
>
> 能移植的是它的**四个设计决定**。这份计划只讲这四个，以及按什么顺序做。

## 一句话对比

| | REA | 我们 |
|---|---|---|
| 输入 | 二进制 / ASAR / APK，**无源码** | **有源码**（139 个仓的 git 镜像） |
| 靠什么理解 | 反编译 + 追踪调用链 | 读源码 + 走导入图 |
| 谁最贵 | 引擎（Ghidra 首次 330 s） | **ssh 往返 + 灌进提示词的 token** |
| 最该抄的 | 证据契约、快照复用、next probes、fail-closed | 同左 |

## 抄哪四条，为什么是这四条

### ① 静态结构分析（`analyze-javascript-application`）

REA 的这条路径**不需要任何引擎**，直接产出 `modules, imports, source maps, routes, IPC and
native add-on relationships`。

我们用得上的是前半段。它证明了一件事：**不装 AST、不装引擎，也能从文件头上抽出足够好的图**。

> 已经在做：`p4-10` 的 `repoIndex`（路由 / 导入 / 符号 + 打分定位）。

### ② 证据契约（`result + evidence_id + limitations/unknowns`）

REA 每个结果都带证据 id 与**明确的不知道**，而且 evidence 可以：
- 单独引用（后来的结论指向前面的 finding，不重跑）
- 导出/导入成 session bundle
- 直接喂给 `compare_functions` / `compare_artifacts` 做版本 diff

我们现在已经有一半：走查的每条结论都指到 `repo:path` 并拿 `lsTree` 核过。缺的是：
- **没有 id**，所以不能引用，只能重查
- **不能导出**，所以半年后无法重放
- **没有版本对比**，只比「PRD vs 现在」，没比「PRD 写的时候 vs 现在」

### ③ next probes（返回「下一步该看哪」，不是返回全部）

REA 对桌面目标返回 `Runtime candidates, supporting files, component markers and **next probes**`。

我们现在是把 28k 字符正文硬塞进提示词。改成「先给候选与理由，由代码按分数选 2–3 个」，
并且告诉模型**还有几个没读**。

### ④ fail-closed 与有界输出

- REA：`字节与声明 hash 矛盾则停止分析`；`超大回复在命令退出后被拒绝`。
- 我们：SHA 中途变了会照常产出半真报告；`show` 超 200KB **静默截断**，模型以为那是全文。

## 分六步，每步可独立验收

### 第 1 步 · 索引与定位（进行中）

| 项 | 内容 |
|---|---|
| 做 | `code_index(repo, sha, files, imports, routes)` + `locate()` 查表打分 |
| 验收 | PAN-6 的 PRD → `search.vue` 第一、`search-entrance.vue` 第二，**<1 s**（现在 29–48 s 且常排错） |
| 降级 | 索引为空（后端仓）→ 退回 grep |
| 依赖 | 无 |

### 第 2 步 · 证据落库（`code_evidence`）

| 项 | 内容 |
|---|---|
| 表 | `code_evidence(id, repo, sha, path, lines, excerpt_hash, retrieved_at, run_id)` |
| 做 | `git show` 拿到的每一段都落一行，返回 `evidence_id`；findings 的 `evidence[]` 改成引用 id |
| 验收 | 同一份走查跑两次，第二次的结论引用**同一批 id**（不重复落库）；把 id 打出来能还原出「哪个 commit 的哪几行」 |
| 为什么 | 这是后面「复用」「对比」「导出」三件事的地基。没有 id，另外三件都做不了 |

### 第 3 步 · 版本对比（`compare_artifacts` 的移植）

| 项 | 内容 |
|---|---|
| 做 | `diffEvidence(a, b)`：两个 `(repo, sha)` 之间，某条结论引用的文件**改了没有、改了什么** |
| 用在 | 走查报告多一栏：「PRD 写在 `afff7295`，现在是 `08230be`，你引的 3 个文件里 1 个已改」 |
| 验收 | 拿 PAN-6 的 PRD 基线 sha 与当前 HEAD 跑一遍，给出「3 条结论中有 N 条引用的文件已变更」 |
| 价值 | 现在走查只说「PRD 和代码不一致」，加了这层能说「**什么时候**开始不一致的」 |

### 第 4 步 · 有界输出与 next probes

| 项 | 内容 |
|---|---|
| 做 | ① 提示词改成候选清单 + 理由（§3.3）② 文件超限**拒绝并说明**，不静默截断 ③ findings 里加 `unread_candidates` |
| 验收 | 提示词里的代码量从 7.7–28k 降到 ≤10k；模型给 `missing` 结论时必须报「还有 N 个候选没读」，N=0 才算「确实没有」 |
| 价值 | 这条直接省钱，也直接治「模型把没看到说成没有」 |

### 第 5 步 · `doctor`

| 项 | 内容 |
|---|---|
| 做 | `npm run doctor`：库连通 / 迁移版本 / 镜像三个仓的 sha 与可达性 / 模型接口 / 企微授权 / 账号与会话密钥 / 磁盘 |
| 验收 | 故意弄坏一项（例如清空 `provider.apiKey`），doctor 指名道姓报那一项，其余仍打 ✓ |
| 价值 | 这一路我手工查过七八次同类问题（provider 被清、镜像没配、企微没授权）。**每次都是二十多分钟** |

### 第 6 步 · 快照导出与 MCP 瘦身

| 项 | 内容 |
|---|---|
| 做 | ① 一次走查/评审的证据包导出成 JSON，可再导入重放 ② MCP 的 16 个工具描述压成一句，详细说明进文档 |
| 验收 | 导出的包在另一台机器上能还原出同样的结论链；`tools/list` 的字符数降一半以上 |
| 价值 | ①是审计能力（半年后能重放），②是每个新会话省几千 token |

## 顺序与理由

```
1 索引      ← 已在做。它同时解决速度和准确率，且不依赖别的
2 证据 id   ← 后面三步的地基。不做它，3/4/6 都缺一环
3 对比      ← 有了 id 才有意义
4 next probes ← 与 2、3 独立，可以先做；但做完 2 之后能一起省 token
5 doctor    ← 与 1–4 完全独立，随时可插入
6 导出/瘦身 ← 最后做，因为它依赖 2 的 id 与 1 的索引
```

**5 可以随时插队**——它不影响别的，而且能立刻减少我们排查环境问题的时间。

## 不移植的（明确写下来，免得以后有人问）

| REA 的能力 | 为什么不移植 |
|---|---|
| 反编译（Hopper / Ghidra / IDA / Juna） | 我们有源码 |
| 进程捕获、ADB、崩溃转储、固件解包 | 我们的对象是 PRD 与实际代码的差异，不是运行时 |
| APK / IPA / EVM / 模型文件分析 | 同上 |
| 26 个 provider 的可插拔体系 | 我们只有一个「源码」来源；模型与镜像传输已经可换，够了 |
| RL 环境构建 | 与产品无关 |

## 一句话总结

**REA 值钱的不是它的工具数，是它对「证据」的纪律**：每个结论带 id、带局限、可导出、可对比、
对不上就停。我们已经在做其中一半（引文逐字核、路径 lsTree 核），这份计划把另一半补齐。

## 度量基线（做完每一项都要给数）

| 指标 | 现在 | 目标 |
|---|---|---|
| locate 耗时 | 29–48 s | 首次 <3 s（含建索引）/ 同 sha <0.2 s |
| 进提示词代码量 | 7.7–28k 字符 | ≤10k |
| 一次评审总耗时 | ~150 s | ≤90 s |
| 结论可重放 | 不能 | 能（导出证据包） |
| 环境故障定位 | 手工 20+ 分钟 | `npm run doctor` 一次 |
