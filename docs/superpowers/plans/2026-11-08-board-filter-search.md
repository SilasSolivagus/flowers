# 看板筛选（按负责人）与搜索

日期：2026-11-08
分支：`main`（基于 `9f836ae`）
一句话：给已经涨到 815 条（收集一列 284 条）的看板加一条工具条——`?q=` 搜标题、`?owner=` 按负责人筛，
过滤**在 SQL 里**做，所以列头那个计数就是筛后的数。十列永远都在，筛空了也还在。

> **多选不在这一轮。** `owner` 是单选：`all` / `me` / `none` / 一个成员 id。
> 同时看两个人需要一套新的 URL 语法（重复参数或逗号分隔）与一套新的交互（多选框而不是下拉），
> 那是一个独立的需求，不是这次「815 条看不清」要解决的问题。这一轮刻意没有它的任何痕迹。

---

## 1. URL 契约

```
/?q=<标题关键词>&owner=<all|me|none|<memberId>>
```

| 参数 | 取值 | 缺省 / 坏值 |
|---|---|---|
| `q` | 需求**标题**的子串 | 缺省、空白 = 不筛；超过 200 字截断 |
| `owner` | `all` · `me` · `none` · 成员 UUID | 缺省 / `all` / 任何认不出的值 = `all` |

- 两个参数都缺 → URL 是干净的 `/`，不是 `/?q=&owner=all`（`boardQuery` 只写非默认值）。
- 同名参数出现两次（`?q=a&q=b`）取第一个，不拼起来：那是两个互相矛盾的指令。
- `owner=<uuid>` 只校验**形状**。UUID 形状但名册里没有这个人 → 一块空看板（`筛出 0 / 815`），
  不静默换成 `all`：把「查一个不存在的人」显示成「全体」等于撒谎，而 `0 / 815` 是真话。
- 手改的 URL 不许 500：`?owner=__proto__`、`?owner=ME`、`?owner=%E4%B8` 一律退回 `all`，
  因为一个非 UUID 的值不会被绑进 `::uuid`（用例逐值跑过）。

解析只有一份：`src/core/read/board-filter.ts`（纯函数，不连库），页面与工具条都调它。

## 2. 搜索只搜标题（owner 裁决）

`q` 只打在 `r.title` 上（`ilike`，ASCII 大小写不敏感、中文原样子串）。

- **不搜编号**。`q=PAN-742` 与 `q=742` 都是 0 条，这是 owner 的裁决，不是漏了。
  理由：一旦「搜 742」既可能命中编号 742、也可能命中标题里的 742，那么「搜到了什么」
  就取决于数据长什么样。用例把这条**否定**钉住了（`不搜编号：PAN-742 与 742 都是 0 条`），
  谁哪天「顺手加一下」`or r.number = 742`，那条会立刻变红。
- **不搜六问正文**。找一条需求时人记得的是名字；全文搜索会把「正文提到过某个词」
  误当成「这件事」。同样有否定用例（正文里的「风控」不算命中）。
- 搜索词里的 `%` `_` `\` 先转义成字面量：用户输入的是字面量，一个 `%` 不该变成「匹配一切」。

## 3. 过滤在 SQL 里做（不是取回 815 行再 filter）

`readBoard(me?, filter?)` 的 where 由 `boardWhere(filter, viewer)` 拼：

```sql
where r.deleted_at is null
  and r.title ilike $1                 -- q（已转义）
  and r.owner_member_id is null        -- owner=none
-- owner=me  → and m.name = $n         （m 就是 owner_member_id 那一行）
-- owner=id  → and r.owner_member_id = $n::uuid
```

三条理由：

1. **列头计数就是被筛的那个数**。八列里有七列筛完会变（收集 284 → 14），
   而列头的 `pill2` 读的是 `column.cards.length`。JS 过滤只能改卡片，要改计数就得再数一遍，
   于是「这一列有几条」有两个来源。
2. **内存里从来没有过没筛的行**。读模型把 `res.rows` 逐行推成卡片，
   没有 `.filter()` 这一步可漏。
3. **分母不能用分子算**。`筛出 N / M` 的 M 是全库未删需求数（815），与筛选无关，
   任何一列都没有它的痕迹。它是**第二条查询**（`count(*)`），两个数各算各的：
   `count(*) over ()` 给的是筛后计数（那是分子），相关子查询在空结果时连一行都返回不出来
   ——而「筛出 0 / 815」正是最需要分母的时刻。两条查询共用同一个 `boardWhere`
   （分母那条传 `NO_FILTER`），所以「什么算一条需求」只有一个来源。

`BoardView` 除了十列还带三个数：`shown`（筛后条数）、`total`（分母）、
`scanned`（这次 SQL 实际返回的行数）。`scanned === shown` 就是「过滤在库里」的证词：
把过滤搬回 JS 时，它会停在 815 而 `shown` 只有十几条。

## 4. UI

`app/components/BoardFilterBar.tsx`（客户端组件）+ `.fbar` 一小段 CSS（`globals.css`，
全部取既有 token 与 `.fld input` 那一套尺寸，没有新控件语言）。

- 搜索框 + 负责人下拉 + 「筛选」+（有筛选时）「清空」+ 右侧灰字 `筛出 N / 815`。
- 是一个 `<form method="get">`：回车或点「筛选」才生效，不是每键一次请求 → **换一条 URL**，
  所以刷新、分享、后退全部自动正确；没有 JS 时它仍是一个能用的 GET 表单。
- 下拉改一下就生效（`onChange` 直接带上当前搜索词跳过去）：选择本身是一个完成的动作，
  再要求点一次按钮是无意义的第二步。
- 工具条是 `.board` 的第一个子项，`position:sticky; left:0`：板子横向滚 2272px 时它还钉在左边。
- 十列永远全建：某列筛完是 0 条时列还在、写着 0。
- 卡片链接与抽屉关闭地址带上当前筛选（`/?open=<id>&q=…&owner=…`）：
  筛出 12 条 → 点开一条 → 关掉，回到的是那 12 条。为此 `Card` 多一个 `query` 参数、
  `Drawer` 多一个 `closeHref`（默认 `/`，行为与以前逐字一致）。

## 7. 仍然粗糙的地方

- **没有多选**。`owner` 只能一个人。多选要新语法 + 新交互，本轮刻意不做（见开头）。
- **没有保存筛选**。刷新能留住（URL 是状态），但没有「存成常用视图」：下一步如果要做，
  应该是服务端一张 `saved_filters` 表 + 一个下拉，而不是塞进 cookie。
- **没有全文搜索**。六问正文、PRD 链接、事件记录都搜不到；这是刻意的（第 2 节）。
- **编号搜不到**。`PAN-742` 是 0 条。要按编号找只能翻列或用浏览器查找——owner 的裁决，
  用例钉住了这个语义。
- **搜索不带高亮**。命中词在标题里原样显示，没有 `<mark>`。
- **`q` 只用 `ilike`**：中文没有分词，`风控` 能命中「分享风控」但 `风 控` 不行；
  真要模糊到这一步应该是 pg_trgm，那是一个索引与迁移的工程，不是这一轮的形状。
- **工具条只在横向滚动容器里 sticky**：纵向滚动交给每一列自己的 `.colbody`，
  所以「滚到第 200 张卡时工具条还在」这句话只在列内滚动的前提下成立（列头也不跟着滚，
  这是看板原有的形状，本轮没有改）。
