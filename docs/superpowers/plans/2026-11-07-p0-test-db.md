## 2. 库选择（`src/db/url.ts`）

```
非测试进程 → DATABASE_URL ?? postgres://postgres:flowers@localhost:54330/flowers   （一字未改）
测试进程   → TEST_DATABASE_URL ?? 把上面的库名换成 flowers_test（主机/账号/query 保留）
测试进程判定：VITEST === 'true' 或 NODE_ENV === 'test'
```

为什么 `TEST_DATABASE_URL` 不做二次纠正：有人把它写错到 `flowers` 时，在这里悄悄改回
`flowers_test` 会把一次真实配置错误掩盖成一次跑绿；正确做法是让它照原样指过去，由守卫在最危险的
那一步之前拦住（见下）。这条留了 `db-url` 与 `reset` 两条用例分别钉住。

## 3. 重置守卫（`src/db/reset.ts`）—— 为什么这么分

`resetDb()` 是 truncate 十一张表 + `restart identity cascade`。以前「用例无条件重置」成立，是因为
用例连的就是 `flowers`；现在用例换库了，若还有人不带守卫地重置一次，配置指错就等于一次静默的数据销毁。

```
shouldAllowReset(database, allowFlag, env):
  测试进程  → /_test(_|$)/.test(database)          // 只看库名形状，**故意不看 FLOWERS_ALLOW_RESET**
  其它      → allowFlag === '1' || database === 'flowers'   // 原口径，脚本用
```

- 测试库必须能清：`flowers_test`、自建的 `flowers_test_ci` 都放行。
- 演示库在测试进程里**永远不放行**，连 `FLOWERS_ALLOW_RESET=1` 也不行——那个口子是给
  `scripts/seed.ts` / `scripts/demo.ts` 手工清演示库留的，测试拿它去清 `flowers` 就是本任务要堵的事故。
- 拒绝时抛的中文报错点名 `TEST_DATABASE_URL` 与 `npm run db:test:setup`，因为这条守卫唯一的现实触发
  场景就是「测试配置指错库」，报错必须直接说怎么办。
- 守卫问的是 `current_database()`（服务端答案），不是 `DATABASE_URL` 字符串——连接串可以被容器端口、
  库别名、缺省值绕过，`current_database()` 与真正会被 truncate 的那张库是同一个东西。
- `resetDb({ guardDatabase, env })` 两个参数**只给用例**：`guardDatabase` 把「守卫以为自己在清哪张库」
  钉成假名字，真连的库不变。这样「守卫被删掉」这个变异能在不瞄准演示库的前提下被用例打红。

## 4. 新开发者要跑的命令

```bash
npm install
npm run db:up             # docker compose up -d db（postgres:17-alpine，宿主机 54330）
npm run db:migrate        # 演示库 flowers 建表
npm run db:test:setup     # 测试库 flowers_test 建库 + 同一批迁移（幂等：库在就跳过建库，迁移按最新一批补齐）
npm run seed              # 演示数据（12 条需求 / 7 成员 / 2 版本）
npx vitest run            # 只碰 flowers_test
npm run demo              # 领域冒烟：仍然清 flowers，跑完要 npm run seed -- --reset
```

三处验证命令的实跑输出：

- `npm run db:test:setup` → `建库：flowers_test` / `迁移完成：flowers_test`（第二次跑 → `库已存在：flowers_test`）
- `npx vitest run` → `Test Files 46 passed (46)` / `Tests 1222 passed | 1 skipped (1223)`
- `npx tsc --noEmit` → 退出码 0

## 6. 变异表（mutation-first）

对每条新用例，把受保护的那一行改坏 → 只跑 `tests/db-url.test.ts tests/reset.test.ts` →
确认红 → 还原（还原后两个源文件与备份 `diff` 无差异）。

| # | 破的行 | 位置 | 结果 |
| --- | --- | --- | --- |
| M1 | `VITEST === 'true'` → `VITEST === '1'` | `src/db/url.ts isTestRun` | 6 红 / 6 绿（exit 1） |
| M2 | `TEST_DATABASE_URL ?? withDatabase(base, TEST_DATABASE)` → 只留后半段 | `resolveDatabaseUrl` | 1 红（覆盖用例） |
| M3 | 删掉 `if (!isTestRun(env)) return base;` | `resolveDatabaseUrl` | 2 红（生产不变用例） |
| M4 | 删掉 `if (isTestRun(env)) return TEST_DATABASE_PATTERN.test(database);` | `reset.ts shouldAllowReset` | 5 红 |
| M5 | `/_test(_|$)/` → `/.*/`（演示库也放行） | `reset.ts TEST_DATABASE_PATTERN` | 3 红 |
| M6 | 删掉 `resetDb` 里的 `if (refusal !== null) throw new Error(refusal);` | `reset.ts resetDb` | 1 红（哨兵行被清，用例同时报「不该被清」） |
| M7 | `options.guardDatabase ?? await currentDatabase()` → 只留后半段（注入失效） | `reset.ts resetDb` | 1 红（哨兵用例） |

每条新断言都有对应的变异能打红；没有出现「代码改坏了用例还是绿」的情况。

## 7. 仍然依赖共享库的部分（没有改，写在这里）

- `npm run seed -- --reset`、`npm run demo`：故意清演示库 `flowers`（非测试进程口径，`FLOWERS_ALLOW_RESET`
  与库名守卫不变）。跑完要重灌。
- `scripts/mcp-smoke.ts`、`scripts/export-queue.ts`、`scripts/migrate-flower.ts`、`scripts/index-*`、
  `scripts/bench-locate.ts`、`scripts/compare-locate.ts`、`scripts/shape-corpus.ts`、
  `scripts/split-description.ts`、`scripts/migrate-line-anchor.ts`、`scripts/wecom-dispatch.ts`：
  都走 `db/client.js`，非测试进程 → 连 `DATABASE_URL`（默认 `flowers`）。它们不在任何用例的子进程里
  （用例的 `execFile` 只起 `git` / `python3`），所以全量测试不会借它们写演示库。
- `npm run dev` / `npm start`：连 `flowers`，与测试无关。
- `flowers_p410`：同一台 postgres 上的一张遗留库，与本任务无关；守卫在测试进程里也不会放行它
  （名字不以 `_test` 结尾）。
- 这台机器上没有 `.env`：默认连接串写死在 `src/db/url.ts`，与 `docker-compose.yml` 的 54330 一致。

## 8. 未做的事 / 风险

- 测试库与演示库共用同一个 postgres 实例与账号：隔离到「库」这一层，不是「实例」这一层。要更硬的隔离
  得给测试单独起容器，那不在这条 P0 的范围里。
- `TEST_DATABASE_URL` 指向一张不存在的库时，报错来自 `pg` 的 `3D000 database does not exist`，
  提示里不会替你跑 setup——`npm run db:test:setup` 写在 README 与本文第 4 节，靠文档而不是靠报错。
- 用例仍然 `fileParallelism: false` 串行跑，且每条重建种子；换库没有改变这个成本。
