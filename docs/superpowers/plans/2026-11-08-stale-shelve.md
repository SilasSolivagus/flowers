## 2. 为什么是「搁置」而不是「拒绝」

`rejected` 与 `shelved` 都是终态，都在看板上离开「收集」。选哪个不是措辞问题，是**库要说实话**：

| | `rejected`（拒绝） | `shelved`（搁置） |
|---|---|---|
| 它断言什么 | 「这件事我们**不做**」——一个**决定** | 「这件事**先不做**」——一个**状态** |
| 谁做过这个决定 | 必须有人：有理由、有当时的信息 | 不需要：事实就是没人接手、没人动过 |
| 半年后翻旧账 | 与「真的评审过、真的毙了」的行长得一模一样，分不出哪条是批量刷的 | 一眼看得出「被批量搁置」，`payload.batch` 还能直接查到是哪一批 |
| 撤回成本 | `rejected → inbox` 在状态机里**没有**这条迁移，只能写手工 SQL | `restore` 一步回 `inbox`，编号 / PRD 链接全保留 |
| 理由 | 必填（`MISSING_REASON_REJECT`） | 必填（`MISSING_REASON_SHELVE`）——两条路都留话，但只有搁置那句是**真的** |

这 34 条没有任何人做出过「不做」的判断。给它们盖上 `rejected`，等于**替人签一次他没签过的字**，
而且签的是一次不可逆的判断（库里没有从 `rejected` 出发的迁移）。`shelved` 只记录已经发生的事实
——192 到 241 天、零业务事件、没有负责人——并且**保持可恢复**。

一句话：**拒绝断言了一个没人做过的决定，搁置只记录已经发生的事实。**

> 把 B 桶称作「批量拒绝的候选集」。那写于裁定之前；裁定的动作是**搁置**。两个文件本次**未改动**

## 5. 事件证据

每行**恰好一条**新事件，形状与 `shelveRequirement` 落的完全一致（`from` / `to` / `reason`
是读侧真正会读的三个键），另加一个 `batch` 标记：

```json
{
  "type": "requirement.shelved",
  "actor": "system",
  "payload": {
    "from": "inbox",
    "to": "shelved",
    "reason": "停 192–241 天且无任何业务活动，按 2026-11-08 过期审计批量搁置",
    "batch": "2026-11-08-stale-audit"
  }
}
```

`events` 总数 865 → **899**（+34），其中 `payload->>'batch' = '2026-11-08-stale-audit'`
的恰好 **34 条**；「这 34 条需求里 `requirement.shelved` 事件数 ≠ 1」的行数 = **0**。

两个标记各管一件事：

- `actor = 'system'`——**不是某个人**。34 条里没有一个「按下按钮的人」，写任何成员的名字都是
  假账（那个人从没做过这个动作，而且站内通知的扇出规则会把「他自己做的」排除掉，于是他一条也
  收不到）。`system` 是本仓库已有的非人 actor（`core/notify/self-heal.ts` 写成员级事件用的就是它）。
- `payload.batch`——**可查询的批量标识**，同时是幂等判据：`payload->>'batch'` 一问就知道这条搁置
  是这批迁移做的，还是哪个人在抽屉里点的「搁置」。

读侧落点：抽屉时间轴显示「搁置 · 停 192–241 天且无任何业务活动…」（`read/detail.ts` 的
`requirement.shelved` 分支），站内/企微通知写「被搁置：停 192–241 天…」（`read/notify.ts`），
事件类 `outcome`（`notify/classes.ts`）。

## 6. 迁移里的四道守卫（宁可不跑，也不猜）

逐条核对，任何一条不成立就 `raise exception`，**整条回滚**（`do` 是一个语句，抛错即全撤，
不会留下半截数据）：

1. **行还在**——查不到就计进 `missing`，**不抛错**（新克隆 / 空测试库 / 别人的库本来就没有这 34 行，
   迁移在那里只能空转，与 `0023` 的 `legacy_ref` 查不到即 0 行同一条口径）。真实库里 `missing`
   一旦不是 0（也不是 34 条全缺），说明连接串指错了库——所以它被报在 `notice` 里。
2. **仍然无主**——有人在这两天认领了它，就是有人接管了这件事，「过期」的前提当场失效。
3. **没被软删**——`deleted_at is null`（与 `0024` / `0026` / `0027` 同一条口径）。
4. **状态是预期的**——要么 `inbox`（本批要收的那批），要么 `shelved` 且那条搁置事件带本批
   `batch` 标记（已经跑过一遍）。其余状态（`design` / `ready` / `dev` / `live` / `rejected` …）
   一律抛错：那说明有人在两天内把它推走了，谁对谁错得人来看。

`update` 自己还带一次同样的条件（`state='inbox' and owner_member_id is null and deleted_at is null`）：
将来上游判断被改坏，这条 SQL 也不会把一条有主 / 已删 / 不在收集的行挪走。

**幂等**：第二遍必然 0 行。已 `shelved` 且带本批事件的行走 `already` 分支；`update` 只认 `inbox`；
`state_entered_at` 也不会被再刷一次。实测重放输出
`0028：搁置 0 条（本批已搁置 34 条 · 库中不存在 0 条…）`，34 行的 `state_entered_at`
**仍是同一个值**（`count(distinct state_entered_at) = 1`），`events` 仍是 899。

## 7. 搞错了怎么退回去

路径就是**现有的 `restore`**，不需要写 SQL、不需要新迁移：

1. 打开该需求（看板「已搁置」列 → 抽屉），或在 MCP 里调 `restore`；
2. 服务是 `restoreRequirement`（`src/core/requirements/terminal.ts`）：`assertTransition('shelved','inbox')`
   → `moveTo(inbox, skip_reason = null)` → 落一条 `requirement.restored`（`{from:'shelved', to:'inbox'}`）；
3. 编号、PRD 链接这些**身份信息保留**；原来的搁置事件也还在（历史不丢，只是多了一条「恢复了」）。

**权限**：`restore` 要 `edit`。这 34 行**没有负责人**，所以没有条线锚点——按 `roles.ts` 的 `can()`，
`edit` 只有**超管**（`product_owner`）拿得到；PM / 条线负责人看不到这个按钮。

**在这 34 行上验证过（只读）**：对真库里全部 40 条「无主 + 已搁置」的行（本批 34 + 0023 恢复的 6 条）
问了一次动作条的真值——

```
无主 + 已搁置的行数： 40
PAN-41  房超=["restore"]  吕品=[]
PAN-51  房超=["restore"]  吕品=[]
房超能恢复的行数： 40 / 40
```

即：超管在这 40 行上都能看到且能执行「恢复」，普通 PM 一个都看不到（不是因为状态，是因为无主）。

**恢复语义在测试库里跑过真服务**（见 `tests/stale-shelve-batch.test.ts` 最后一组）：34 行搁置 →
超管 `restoreRequirement` 其中一条 → 回 `inbox` + 一条 `requirement.restored` → **再跑一遍迁移，
它不会被搁回去**。这条是刻意的：某条需求已经有本批的搁置事件却又回到 `inbox`，形状就是
「人按过一次恢复」——那是对这批决定的一次否决，迁移不该替他撤销。所以「第二遍 0 行」与
「撤回留得住」是同一件事的两面。

## 9. 已知副作用与没做什么

- **超管会收到 34 条「被搁置」的站内 / 企微通知**。扇出规则是「超管收每一条变更、排除自己做的」，
  而这批事件的 `actor` 是 `system`，不属于任何人 → 不会被排除。34 条一次性事件，落在同一分钟。
  如果不想要这批噪音，做法是给这 34 条事件加一个 `actor` 的白名单/静音规则——那是通知口径的
  改动，超出这次裁定的范围，所以只记在这里。
- **没有动 `src/core/requirements/stale-audit.ts` 与 `2026-11-08-stale-audit.md`** 里「批量拒绝」
  的旧措辞（约束：不碰读路径与审计口径，见第 2 节末尾那一段引用）。
- **没有写 `review_assignments`**：一次真实搁置会顺手作废还挂着的派单（`terminal.ts` 里那条
  `update`），但这 34 行全在 `inbox`、连一条评审事件都没有，那条 SQL 在这里命中 0 行；
  写了就是「顺手改第三个表」，而这次裁定的范围只有这 34 条需求的状态。
- **`state_entered_at = now()`**：它们今天真的进入了「已搁置」，看板上「搁了 N 天」从今天起算。
  与 `0023` 刻意相反——那批行状态没变过（是被 `0021` 误移的），原始时刻才是事实；这里状态变了。
- **迁移不许读 JSON**：那 34 个 id 是生成后写死在 `0028` 里的（一行一条带 PAN 号）。JSON 与
  迁移的一致性由用例第 1 组守——以后如果有人改了审计口径，先红的是那条用例，不是生产库。
