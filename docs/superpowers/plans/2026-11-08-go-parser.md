# Go 解析器（2026-11-08）：索引第一次能看见后端

**一句话**：`outlineOf` 多了一条 Go 分支（`func` / 方法 / `struct` / `interface`），`.go` 进了
`CODE_EXT` 并一律判 `service`，Go 的 `imports` **故意留空**。拿 `apisrv` 做实验仓接进来一节：
**583/624 文件进索引，561 个文件有 outline，2810 个节点**，与 `git grep` 逐行对账**零漏零多**
（比 grep 还准两处，见 §5）。

---

## 0. 为什么要做（这次不是猜的）

索引只读 `[ts|tsx|js|jsx|mjs|cjs|vue]` 与 `pages.json`，于是：

- `123pan-gateway` 接进来、镜像绿了、同步绿了，覆盖率一行写着 **0/49**——仓在，索引看不见；
- 清单里 **79 个 Go 仓**因此一个都没接（`config/repos.txt` 里那段注释就是当时的判断依据）；
- 而需求侧 **35 条活需求**挂着 `backend` 平台（平台分布：web 277 / mobile 225 / pc 220 /
  mini 46 / **backend 35** / admin 17 / manager 13 / h5 10）。对这 35 条，材料今天只能说
  「后端要配合改」，说不出改哪儿。

`apisrv` 是那 35 条的主 API 服务器（「处理客户端所有请求」），所以它既是解析器的对照组，
也是这次唯一要接的仓。

## 1. 改了什么（三处，都在 `src/core/codemirror/code-index.ts`）

| 位置 | 改动 | 裁决 |
| --- | --- | --- |
| `OutlineNode.kind` | 加 `go-func` / `go-method` / `go-struct` / `go-iface` | 四种分开而不复用 `symbol`：「有没有这个方法」与「有没有这个结构体」是两个问题，混成一个 kind 之后调用方还要回头解析名字 |
| `CODE_EXT` | 加 `go` | `.go` 进索引的前提 |
| `classifyKind` | `.go` **先判**，恒 `service` | 见 §2 |

| `maskCode` | 新参数 `rawBacktick`（默认 false = JS 口径） | 复用同一个抹除函数，不写第二套（见 §2.3） |

### 2.1 `imports` 对 Go 恒空（**故意空着，不是没做完**）

`imports` 这张图的单位是**文件**（`path → 仓内文件路径`），而 Go 的导入单位是**包（一个目录）**。
`apisrv` 的 import 写的是完整模块路径：

```
import (
	"codeup.aliyun.com/60f9058e68e2993a8e6d0750/123pan/apisrv/app/grpcserver"
)
```

要落地必须先把模块前缀摘掉——而模块根不一定是仓根（`cmd/x/go.mod` 这种多模块仓），前缀还随
`go.mod` 的 `module` 行变。就算摘对了，拿到的仍是一个**目录**，目录里有 N 个文件；随便挑一个写进
`imports` 就是**编一条边**，而 `importedBy` 会照着这条假边回答「改它会波及几个页面」。

这个仓已经被「猜」坑过一次（`resolveSpecifier` 的后缀兜底就是这么长出来的：只在唯一命中时才采纳）。
所以 Go 这一半的结论是：**一条错的边比缺一条边糟，宁可空着**。

代价说清：Go 文件的定位只能靠「目录/文件名 + outline」，走不了一跳图；`locateAcross` 的
`imported` 那 4 分对 Go 永不生效。要补这一层，得先有「包 → 代表文件」的定义（谁代表一个包？
`doc.go`？`init.go`？），那是另一个决定，不在这次的范围里。

防御是两层的：`parseBlob` 不抽 spec；`RESOLVE_EXT` 里也没有 `.go`——所以即使有人把第一层拆了，
一条 `import "service/folder.go"`（恰好就是仓内路径）也**不会**落地。用例把这两点都钉住了
（`连「恰好是仓内路径」的说明符也不落地`）。

### 2.2 `.go` 判 `service`，`_test.go` 不进索引

`FileKind` 是**前端角色**的轴（page / component / service / state / route）。Go 仓里没有「一屏」
也没有「可复用组件」：`apisrv/component/` 是一个**库包**、`app/` 是 handler、`service/` 是业务层、
`library/` 是工具层——它们的角色完全相同：服务端实现。

沿用目录约定会怎样（两条都试过）：
- `component/` 命中 `COMPONENT_DIR` → 判 `component`，于是定位排序把它当「前端组件」抬到页面前面；
- `app/` / `library/` / `constvar/` 命中不了任何规则 → 判 `other` → **等于不进索引**，整个仓又变 0/624。

两种错法都不如一个诚实的桶：`.go` = `service`。

`_test.go` 整类不进索引：`TestCreateFolder` 命中「文件夹」时 `locate` 会把它当候选，材料照着测试名
说「已有创建文件夹的接口」——那是把**测试**当**产品**。`apisrv` 里这样被主动不看的有 **33 个文件、
86 条声明**。代价：覆盖率的分母（`ls-tree` 总数）里还有它们，所以 Go 仓的
`files_indexed/files_total` 天生小于 1（583/624 就是这件事，不是漏索引）。

### 2.3 `maskCode` 扩一个参数，而不是写第二套

Go 的反引号是**原始字符串**，`\` 不是转义。沿用 JS 口径（`\` 吃掉下一个字符）时，`` `C:\` ``
结尾那个反引号会被当成「被转义的字符」，字符串一直抹到下一个反引号——中间的真声明全部消失，
或者引号错位之后**编出**假声明。所以 `maskCode(text, { rawBacktick: true })`：默认仍是 JS 口径
（`.tsx` / `.ts` 的调用方一个字都没改），Go 显式打开。抹成空格而不是删掉，理由与原来同一条：
**行号必须留在原地**。

## 3. 抽取规则（正则，锚在行首）

| 形态 | kind | 名字 |
| --- | --- | --- |
| `func Name(` / `func Name[T any](` | `go-func` | `Name` |
| `func (r *Recv) Name(` / `func (Recv) Name(` / `func (r *Recv[T]) Name(` | `go-method` | `Recv.Name` |
| `type X struct` | `go-struct` | `X` |
| `type X interface` | `go-iface` | `X` |
| `type (` … `)` 块里的 `\tX struct` / `\tX interface` | 同上 | `X` |
| `func init()` | **跳过** | — |
| `_test.go` 整个文件 | **跳过** | — |

**方法名带 receiver**（`identifyService.IdentifyInfo`）不是装饰：`apisrv/service/` 里 `List`、`Get`、
`Handle` 这类名字在十几个 receiver 上重复出现，只留 `Handle` 的材料说不出「谁的 Handle」。

**为什么是正则不是 AST**（选型就写在这里，别下次再问）：tree-sitter / `go/parser` 都是新依赖，
而这一层要回答的问题只有一个——「这个文件里有哪些函数/方法/类型」。Go 有一条对正则极友好的性质：
`gofmt` 把每条顶层声明都顶在第 0 列、以 `func` / `type` 开头，于是 `^func` 这种锚点不需要任何缩进
推断（对比 `.ts` 那半边必须逐行猜 `export`）。

## 4. 正则**抓不到**什么（具体，不含糊）

1. **接口里的方法行**：`type Pager interface { Page() int; SetPage(n int) }` 里那两行没有 `func`
   关键字，一个都抽不到——只有 `Pager` 这个名字进 outline。要修只能进 AST。
2. **多行 receiver**：`func (\n\ts *Server,\n) Name(` 会漏。`gofmt` 不这么排版，只在手写/生成代码里出现。
3. **泛型约束里带换行或嵌套括号**：`func F[A interface{ M() }, B any]()` 能抽出名字 `F`（`[([]` 认
   左括号），但 `[` 之后的内容不校验——名字对了，签名理解不了。
4. **构建标签**：`//go:build windows` / 文件名后缀 `_windows.go` 不看，同一个包里各平台的实现都会
   进 outline（`apisrv` 目前没有这类分叉）。
5. **`var` / `const` 块**：`var x = ...`、`const (` 一律不进 outline（这次只要四类声明）。
6. **函数体里的东西**：Go 没有嵌套具名函数，闭包不是声明——正确跳过，但也意味着「某个 struct 的
   字段」不在 outline 里（`type file struct { … }` 只给 `file`）。
7. **同一行的多条声明**：`func (s Store) Len() int { return 0 }` 这种单行方法体，抽得到名字；
   但 `var a, b = 1, 2` 之类不在范围内。
8. 抹除口径的残留：`maskCode` 不认识正则字面量（`/<[A-Z]/`，JS 侧老问题），Go 侧没有正则字面量，
   这一条不影响 Go。

## 6. 这份 outline 让材料多说了什么（一句能落地的）

需求 **#613《自定义域名备案失效告警与分享页独立 CNAME》**（`platforms @> '{backend}'`，live）：

## 8. 79 个仓一起接的剩余风险（先别接）

1. **`vendor/` 目录**：`mirror.ts` 的 `NOISE_DIRS` 里有 `vendor_bundle`，**没有 `vendor`**。一个开了
   `go mod vendor` 的仓，树里会多出几万个 `.go`——它们全会被判 `service`、全会被读内容、全进
   `blob_index`。`apisrv` 没有 `vendor/`，所以这次没暴露；79 个里只要有一个，就是一次体积爆炸。
   **接之前要先决定 `vendor` 进不进噪音（我倾向：进，与 `node_modules` 同一条理由）。**
2. **生成代码占多数**：`apisrv` 的 1003 个 struct 里绝大多数来自 GoFrame 的生成器
   （`app/model/*`、`app/dao/internal/*`，文件头就写着 `DO NOT EDIT`）。outline 会把它们当产品
   类型报出来——材料说「已有 UserVip 这个结构体」是真话，但「改 UserVip 就能改会员」是假话。
   79 个仓一起接之前，得先有一个「生成文件」标记（文件头 `DO NOT EDIT` / `// Code generated`）。
3. **没有导入图**：35 条 backend 需求的「波及面」只能靠 `locate` 的名字+符号分，答不了「改它会
   影响几个 handler」。这不是解析器的 bug，是 `imports` 故意空着的代价（§2.1）。
4. **`locate` 的 `symbol` 那 3 分对 Go 不生效**：`exportsOf` 只认 `export` 关键字，Go 一个都没有
   （583 个文件的 `exports` 合计 0 条）。所以 Go 文件的候选来自「目录/文件名」6 分与路由 10 分
   （Go 没路由，实际只有 6 分）。要不要把 outline 的 `go-func` 名字也喂进 `exports` 是**另一个决定**：
   那会改 `locate` 的评分输入，而「不动评分」是这次计划的非目标。
5. **接口方法抽不到**（§4 第 1 条）：如果哪天要回答「这个仓实现了哪些 RPC 方法」，接口那一半是空的。
6. **磁盘**：这次实测 0.367 GB/仓 → 139 仓外推 51 GB（中位数外推，样本只有 1 个，别当承诺）。
   79 个 Go 仓若多数在 0.4 GB 量级，约 32 GB——`dogyun` 现在剩 46 GB，**装得下但不宽裕**。
