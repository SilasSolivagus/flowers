## P0 · 测试用独立数据库（已完成，见 `2026-11-07-p0-test-db.md`）

**状态**：已实施。与下面这份原计划有三处出入，按实测改写：

1. 库选择抽成纯函数 `resolveDatabaseUrl(env)`（`src/db/url.ts`），`client.ts` 只负责建 Pool。
2. 守卫**不放在脚本里、放进 `resetDb()` 自身**（truncate 之前），判据不是白名单
   `['flowers','flowers_test']`，而是「测试进程只放行名字以 `_test` 结尾的库，且故意不看
   `FLOWERS_ALLOW_RESET`」——白名单只认识一个名字，且挡不住 `FLOWERS_ALLOW_RESET=1` 这条捷径。
   配置指错时 `resetDb()` 当场抛错、一张表都不清，比「静默截断」强。
3. 建库脚本是 `scripts/db-test-setup.ts`，命令即计划里的 `npm run db:test:setup`（幂等）。

**目标**：`npx vitest run` 不再碰 `flowers`，改碰 `flowers_test`。

**做法**
- `src/db/client.ts` 的 `DATABASE_URL` 读取加一道：当 `NODE_ENV === 'test'` 或 `VITEST === 'true'` 时，默认取 `flowers_test`（可被 `TEST_DATABASE_URL` 覆盖）。
- `src/db/reset.ts` 的允许列表从 `['flowers']` 改成 `['flowers', 'flowers_test']`——**两个都允许，因为测试库必须能重置，而演示库只允许脚本显式重置**。
- 新建测试库：一个 `npm run db:test:setup`（建库 + 跑迁移），写进 README。
- 验证：跑完全量测试后，`select count(*) from requirements` 在 `flowers` 里**不变**。

**验收**
- 全量测试绿，且 `flowers` 的 12 条演示数据在测试前后逐条相同（比 id 集合）。
- `flowers_test` 里表结构与 `flowers` 一致（迁移跑过）。

**风险**（已扫）：`scripts/*` 里有脚本直连 `flowers`，若它们被测试间接调用会写错库——扫一遍 `db/client` 的引入点。
实测：脚本只被人工调用，用例里的 `execFile` 只起 `git` / `python3`，没有任何子进程会跑 `scripts/*`；且脚本走的是同一条 `db/client`，测试进程里自然落到 `flowers_test`。清单见报告第 7 节。

## P1 · 803 条全量迁移

**目标**：线上 Flower 的 803 条（含 264 条已上线）进新库，状态/优先级/平台/类型按 `migrate-flower.ts` 的映射落位。

**做法**
- `npm run migrate:flower --apply`，**先 dry-run 存一份基线**（803 条的状态分布、逐条 number→state），apply 后再读一遍，两份比对。
- 幂等：按 Flower 的 uuid 跳过已存在（脚本已有此逻辑），再跑一次必须 0 新增。
- 回滚：迁移写入的行带 `legacy_ref`（Flower uuid），回滚 = `delete where legacy_ref is not null`；**先在一张临时表上演练一次**再动真库。
- 迁移后自检：条数=803、11 个旧状态各自的落点计数与 dry-run 一致、priority 分布与线上一致（800 条有值）、platform 12 端分布抽查 10 条。

**验收**
- 条数与分布对上；再跑一次 0 新增；回滚演练通过（演练完恢复）。
- 看板上能看到 803 条真实需求，列数/顺序正常。

**已知数据缺陷（要在报告里写，不许悄悄修）**
- 463 条没有条线 → 默认 feature（`type` 必填）
- 1 条复合平台值无法表示为多值

## P1 · 导出按钮

**目标**：不敲命令也能把「待排期」导成企微智能表格。

**做法**
- 看板「待排期」列头加一个入口（仅当列非空）；抽屉里不放（那里是单条）。
- server action：调用现有的导出逻辑（把 `scripts/export-queue.ts` 的核心提到 `src/core/export/queue.ts`，脚本与按钮共用）。
- 成功后返回文档链接，界面显示「已生成」+ 链接；失败给中文原因（企微未授权 / 无待排期 / 网络）。
- 权限：任何能看板的人都能导（导出的是他能看到的数据）。

**验收**
- 点一次真建出表（行数=待排期条数，列=9）；链接可点开。
- 待排期为 0 时按钮不出现（不是点了报错）。

## P2 · 企微绑定自愈

**现状**：绑定要手动点「查一下」；失效后没人知道。
**做法**：`tick` 时检查——`notify_prefs.wecom !== 'off'` 且 `wecom_userid is null` 或连续失败 ≥3 次 → 给超管一条站内提醒（每人每天最多一条）。

**验收**：把某人的 userid 清空，跑一次 tick，超管铃铛里出现一条中文提醒；同一天再跑不重复。

## P2 · MCP 只读工具接权限

**现状**：读工具按状态返回动作，没有和 `can()` 交集（p4-05 遗留）。
**做法**：`mcp/tools.ts` 里凡是返回 `actions` / `permissions` 的地方，一律过 `can(actor, facts, …)`——token 的身份就是那个成员，不该看到自己没有的按钮。

**验收**：造两个 token（吕品 / 赵越），分别读同一条「商业类、负责人吕品」的需求，返回的 actions 不同；PM 读别人的需求只读。

## P2 · 同线多负责人时派单选人

**现状**：固定取第一个人。
**做法**：按「不是需求负责人本人」优先，其次「该线负责人里最近有活动（events）的」，再次按 id 稳定。写清规则并测试。

**验收**：同线两个负责人时，派单不会派给需求负责人自己；结果稳定（同输入同输出）。
