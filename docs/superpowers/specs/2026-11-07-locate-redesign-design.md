# 「找到代码现状」这件事重做：两套入口，先说不知道

状态：待实施
日期：2026-11-07
前置：`plans/p4-10-static-index-design.md`（本文推翻它对「索引负责定位」的定位）、
`plans/p4-12-rea-port-plan.md`（本文替换它的第 3–4 步）

## 1. 为什么要重做

### 1.1 实测数据

同一份 PAN-6 的 PRD，两条路径对比（`scripts/compare-locate.ts`，A 半边已冻结）：

| | 老办法（ssh grep + 中文词表） | 静态索引（路由/导入/符号） |
|---|---|---|
| 耗时 | 2,594 ms | **223 ms** |
| 进提示词 | 7,457 字 | **734 字** |
| 正确答案排名 | 第 1、第 2 ✅ | 第 1、第 2 ✅（修 `locateAcross` 之后） |

**看起来是完胜。** 但换 7 条真实需求重测（`scripts/bench-locate.ts`，标准答案来自 git 合并历史）：

```
第 1 名命中    老办法 1/7   ·   索引 0/7
```

**一条案例上成立，七条上不成立。** PAN-6 是特例：它的中文词与文件名同源（「搜索」→ `search.vue`），
是所有情况里最顺的一种。

### 1.2 真正的病灶

两条路都卡在同一步：**把中文需求变成英文代码路径**。

```
需求标题  用户部分权益缩减调整
    ↓ 靠一张 30 个词的人工对照表猜
代码路径  src/pages/video/video.vue      ← 字面上毫无关系，永远猜不到
```

「权益缩减」这个改动落在 `video.vue`、`questions.ts` 里，任何词表都不可能猜出来。

### 1.3 一条没说过的线索

git 历史里有 **657 条合并记录**，每条都带**中文**提交信息与改动文件：

```
feat: 用户权益缩减                          → video.vue / questions.ts
feat: 下载限速风控开发                       → common-modal.vue / file-actions.vue
feat: 动态域名入口切换至123panapi.com         → …
```

用「需求标题 ↔ 中文提交信息」的相似度检索，再取那次合并改过的文件——**实测 7 条里 5 条把
正确的那次合并排进前 4 名（共 657 条）**，且全程不做任何中英翻译。

## 2. 目标与非目标

### 目标

1. 走查（代码已存在）与评审（代码可能未写）**分开设计**，各有自己的信号与本分。
2. 第一版**不允许材料里出现「这个功能就在这里」这种肯定句**——只允许「线索」与「不知道」。
3. 把「找不到 / 不确定 / 命中」记成账，攒够 30 条人工案例后再定准确率门槛。
4. 读不到代码时必须明说，不许静默降级成「代码里没有」。

### 非目标

- 不追求第一版的高准确率。第一版追求**不骗人**。
- 不做向量检索、不引入 embedding 依赖。
- 不做「人工指路」交互（评审为方案 A：只给提示，不要求人填路径）。
- 不覆盖后端仓库（Go/Java）——本期只有两个前端仓。

## 3. 总体结构

方案 1：**两个模块，共享小球**。

```
src/core/locate/types.ts        候选的形状：{ path, reason, confidence, source }
src/core/locate/copy.ts         「定位不到」的那几句话（唯一来源）
src/core/locate/history.ts      走查：中文提交信息检索 → 文件
src/core/locate/structure.ts    评审：结构索引 + 模型扩展词 → 文件
```

两条路各自独立、各自测试；共享的只有**候选的数据形状**与**那几句话**。

**为什么不抽一个统一框架**：两条路的失败方式不同（走查是「历史里没有」，评审是「代码还没写」），
置信度算法也不同（一个看提交相似度，一个看结构命中）。强行统一是假抽象。

## 4. 数据：`commit_history`

```sql
create table commit_history (
  repo        text        not null,
  commit_sha  text        not null,   -- 合并提交本身
  merged_at   timestamptz not null,
  branch      text,                   -- feat-userEquity-fjd
  message     text        not null,   -- 该分支全部非合并提交信息，拼接
  files       jsonb       not null,   -- 该次合并动过的源码文件
  primary key (repo, commit_sha)
);
```

### 三个决定

1. **粒度和「一次合并」对齐。** 一次特性分支合并 = 一个功能落地；分支中间的
   `fix: 改个字母` 不是功能单位。
2. **`branch` 也存。** `feat-userEquity-fjd` 里的 `userEquity` 是唯一白给的中英对照线索；
   它是数据，不是手写词表，将来可据此自动造词表。
3. **中文信息全留，不只取第一条。** 一个分支里可能有三条提交信息，合起来才是完整描述。

### 建立与维护

| 时机 | 做什么 | 代价 |
|---|---|---|
| 首次 | 每个仓扫一遍全部合并历史 | uni-app 85 条 + pc 173 条，约 40 s |
| 之后 | 只补 `merged_at` 比库里最新更新的 | 几秒 |

历史只增不改，所以「缺就补」永远安全，无需失效逻辑。

### 已知边界

**只认「走分支再合并」的改动。** 直接推主干的提交、revert、跨仓联合改动都抓不到。
这意味着部分需求在走查时**必然**落到「不知道」——这是方法的边界，不是故障。

（已与 owner 确认：开发确实都走「开分支 → 合并」。）

## 5. 走查路径（`history.ts`）

### 检索

1. 查询词与每条 `message` 都切成小块：中文按二字组，英文按单词。
2. 用 IDF 加权：出现在少数提交里的词（「权益」「限速」）比到处都有的词（「视频」「文件」）分量重。
3. 按相似度排序，取**前 5 条**合并（暂定 5，等评测集够了再调）。
4. 把这 5 条改过的文件并起来，按**出现次数**排序——被两三次合并都改过的文件，比只出现一次的更像「功能所在」。

### 输出

3–5 个候选，每个带出处：

```
src/pages/video/video.vue
   ← 出自 2026-11-03「用户权益缩减」那次合并
```

### 置信度

第一版**一律 `low`**。理由：7 条实测里最好的一条路也只对 1 条，没有资格给 `high`。

### 空结果

相似度全低或无从比对时返回空，由输出层说「不知道」。

## 6. 评审路径（`structure.ts`）

### 为什么用另一套

评审发生在代码可能还没写的时候，历史表里没有这条记录——第 5 节的机制不适用。

### 两步

1. **让模型先想「这个需求大概会叫什么名字」**：给出 5–8 个中文说法 + 英文词 + 可能的位置。
   例：「权益套餐产品结构改造」→ 权益/套餐/会员/付费 · vip/equity/member/package · 会员中心/支付页。
2. 拿这些词去**结构索引**（`code_index`，路由 10 / 文件名 6 / 被引用 4 / 导出符号 3）检索。

相比手写词表：手写表给一个方向（「权益」→ vip），模型给四个方向且带中文。

### 成本与风险

- 成本：每次生成多一次模型调用，约 2 s。
- 风险：模型可能想出与代码无关的词。因此扩展词**只用于检索，不用于下结论**，结果一律 `low`。

### 输出

同一形状，但措辞不同：这是「最可能的位置，待研发确认」，不是「现状」。

## 7. 输出契约（材料里写什么）

三种情况，只有前两种在第一版出现：

**① 一个都没找到**（或代码没读到）

> 这条需求没能在代码里定位到实现，因此**下面不包含现状判断**。
> 请与研发确认现在实际是怎么做的，确认后**更新 PRD 文档**，材料会标记为旧版并重新生成。

**② 找到候选，但不确定**（第一版的常态）

> 最可能的位置（**待研发确认**）：
> - `src/pages/video/video.vue` ← 出自 2026-11-03「用户权益缩减」那次合并
>
> 以上是线索，不是结论。确认后请更新 PRD 文档。

**③ 确定** —— 第一版不做。开放条件：人工案例攒到 30 条且达到届时定下的门槛。

### 为什么推动 PRD 而不是六问

人跟研发聊完会去更新**正式 PRD**，不会回来填我们内部那六个格子。材料要推动他们本来就会做的动作。
链路已经通了：PRD 变 → 快照比对 → 材料标「需求已更新」→ 重新生成读到新 PRD。

### 记账

每次落到 ① 或 ② 都记一条（时间、需求、档位、候选数、命中与否），攒够 30 条人工案例后再定门槛。

## 8. 失败与降级

| 情况 | 行为 |
|---|---|
| 镜像读不到 | 明说「代码没读到（原因）」，**不许**降级成「代码里没有」。这是 `fail-closed` 的教训 |
| 读到了但历史表未建 | 走查退回结构路径，置信度再降一档，材料写明 |
| 模型扩展词调用失败 | 用原始关键词跑结构，不重试、不报错，标 `low` |
| 评测脚本跑不起来 | **不算通过**。尺子坏了不能当成量出来是好的（本次差点犯：对比脚本漏了中→英映射，两边都 0，看起来像「都找不到」） |

## 9. 评测

两把尺子，**分开看，不合并成一个百分比**：

| 面 | 来源 | 用途 | 局限 |
|---|---|---|---|
| 面一 | 人工配对的 7 条真实需求 | **说了算**：判断准不准 | 少；且已反复看过，易被无意调参 |
| 面二 | 657 条合并，用其自身的提交信息当查询 | 抓「大面积崩塌」（改了算法后从 60% 掉到 5%） | **有泄漏**：查询来自答案那次合并 |

指标：

- 正确答案是否出现在交出去的文件清单里（recall，不是 rank 1）
- 「一个都没找到」「不确定」「命中」三档各占多少

门槛：**第一版不设数字**。人工配对案例 ≥ 30 条后再用真实数据定，不拍脑袋。

## 10. 实施顺序

1. `commit_history` 表 + 建立脚本 + `--dry-run`（能在本机打印索引摘要）
2. `history.ts` 检索 + 单元测试（含「历史里没有 → 空」）
3. `structure.ts` 接模型扩展词 + 单元测试（扩展词失败要降级）
4. 输出契约：两档措辞 + 找不到时的句子 + 记账表
5. 接线：`inspect.ts` 走历史，`review.ts` 走结构；`fail-closed` 改造
6. 评测：用 7 条跑一遍，记录三档分布；把面二跑到 40 条以上

第 1、2 步可独立验收（不进材料也能看「找到什么、多快」）。
