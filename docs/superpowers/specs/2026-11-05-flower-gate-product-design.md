# Flower 闸门 · 产品设计 v1

- 日期：2026-11-05
- 状态：设计已逐条确认，待评审
- 边界：只做**需求的状态机、关卡签字、通知**。不做文档正文、任务、迭代、负载、统计看板。

---

## 1. 一句话

需求从进来到上线，只有 **10 个状态**、**4 个需要人动手的时刻**，其余全由时钟推进。
机器负责生成材料（UEmaster）和比对，**人负责点头**。

## 2. 角色

| 角色 | 谁 | 能做什么 |
|---|---|---|
| PM | 房超 · 王妍 · 吕品 · 李嘉 | 建需求、评估、提交评审、排期、打回、搁置 |
| 商业线评审人 | 赵越 | 评审**商业类**需求；**同时也带自己的需求**，PM 的全部能力他都有 |
| 功能线评审人 | 吕正豪 | 评审**功能类**需求；**同时也带自己的需求**，PM 的全部能力他都有 |

- **评审人由需求的「类型」决定**，不是由人挑。
- 待评审期间改类型 = 换评审人：已签的字作废，重新派单。

## 3. 状态机（10 个状态）

```
inbox → 待设计 → 待评审 → 待排期 → 待开发 → 开发中 → 测试中 → 已上线
  ↓        ↑ 打回        ↓ 打回              ↖ 打回 ──┘
已拒绝   已搁置(→恢复回 inbox)
```

| # | 从 → 到 | 触发 | 门（不满足不让过） |
|---|---|---|---|
| 1 | inbox → 待设计 | 点「评估」 | 出 UEmaster（需 LLM，未配置则按钮灰） |
| 2 | inbox → 待评审 | 直接提交 | **正式 PRD 链接**（一个 URL 即可；记一条跳级事件） |
| 3 | inbox → 已拒绝 | 点「拒绝」 | 无 |
| 4 | inbox → 已搁置 | 点「搁置」 | 无 |
| 5 | 待设计 → 待评审 | 上传 PRD 并提交 | **正式 PRD 链接** |
| 6 | 待评审 → 待排期 | 评审人点通过 | 评审人 = 类型对应的人 |
| 7 | 待评审 → 待设计 | 评审人打回 | 打回原因 |
| 8 | 待排期 → 待开发 | 排进版本 | **版本 + 提测日 + 承诺完成日** |
| 9 | 待开发 → 开发中 | 时钟：到开工日 | 无人工动作 |
| 10 | 开发中 → 测试中 | 时钟：到提测日 | 无人工动作 |
| 11 | 测试中 → 已上线 | 时钟：到承诺完成日 | 无人工动作 |
| 12 | 测试中 → 开发中 | 点「打回」 | **必须重填承诺完成日** + 原因 |
| 13 | 已搁置 → inbox | 恢复 | 无 |
| — | 已上线 → 走查 | 点「走查」 | 生成 UEmaster；**不改状态** |

**每个状态都可搁置**（已拒绝 / 已搁置除外）；**只有 inbox 可拒绝**。

## 4. 时间与承诺

三个日期，两把锁：

| 日期 | 层级 | 谁定 | 改的时候 |
|---|---|---|---|
| 版本时间窗（开始 / 发版） | 版本 | 评审后一次定 | 改期要写原因 |
| 提测日 | 需求 | 排进版本时 | 同上 |
| 承诺完成日 | 需求 | 排进版本时 | **打回必填新的** |

- 后三个状态（待开发 / 开发中 / 测试中 → 已上线）**由时钟推进**，没有「认领」「验收」这类人工动作。
- **打回必须重算承诺完成日**：状态可以回退，时间不能沿用，否则倒计时不停，到点又被自动推成已上线。
- 「时间已用 %」= 今天在 [承诺开始, 承诺完成日] 区间里的位置；没排期则不显示。

## 5. 三处 UEmaster

| 环节 | 状态 | 输入 | 产出 | 谁判 |
|---|---|---|---|---|
| 评估 | inbox | 需求描述 | 流程图 + 原型页（讨论材料） | 人 |
| 评审 | 待评审 | 正式 PRD | 同上 + 问题清单（死路 / 缺页面 / 缺状态 / 歧义词 / 未知角色） | 评审人签 |
| 走查 | 已上线 | 代码 + PRD 版 | 实际版 + 与 PRD 版的差异清单 | 人看，不改状态 |

三份产物都存**链接 + 生成时间 + 版本号**，不存正文。

## 6. LLM 从哪来

UEmaster 是「提示词 + 排版脚本」，不是模型。所以不打包进 MCP，**借调用方的模型**。

MCP 两个动词：

```
uemaster.plan(requirementId, stage) → 任务包：PRD 全文 + 页面清单要求 + 版式规范 + 输出契约
uemaster.attach(requirementId, url) → agent 生成完 HTML，把链接交回来
```

按钮三态：

1. 组织配了 key → 后端调（BYO）
2. 没 key，但在 MCP 会话里 → agent 生成
3. 都没有 → **按钮灰**，悬停必须说明原因与解法：`未配置模型 · 去设置配置，或让 agent 生成`

**没有 LLM 时系统仍可用**：评估只是加速器，`inbox → 待评审` 永远开着，只要给 PRD 链接。

## 7. 数据模型（增量）

在现有 `requirements` 上加：

| 字段 | 说明 |
|---|---|
| `type` | `commercial` \| `feature`，**录入必填**，决定评审人 |
| `prd_url` | 正式 PRD 链接 |
| `commit_test_at` | 提测日 |
| `commit_due_at` | 承诺完成日（打回必填新的） |
| `state_entered_at` | 进当前状态的时刻，算「停在这几天」 |
| `skip_reason` | inbox 直接跳待评审时的原因 |

新增两张表：

| 表 | 用途 |
|---|---|
| `uemaster_artifacts` | requirement_id, stage(evaluate/review/inspect), url, version, created_at |
| `review_assignments` | requirement_id, reviewer_member_id, signed_at, verdict, reason（改类型时置作废） |

## 8. 通知

| 事件 | 发给谁 | 渠道 | 时机 |
|---|---|---|---|
| 进入 inbox | 提出人 + PM | 站内 | 立即；停留超 3 天每天提醒 |
| 进入待设计 | 负责人 | 企微 | 立即：尽快出正式 PRD |
| 进入待评审 | **类型对应的评审人** | 企微 | 立即；超 1 天再提醒 |
| 评审打回 | 负责人 | 企微 | 立即，带原因 |
| 进入测试中 | 负责人 + 测试 | 站内 | 立即 |
| 测试中被自动上线 | 负责人 + 评审人 | 企微 | 上线时 |
| 打回开发中 | 负责人 + 测试 | 企微 | 立即，带新承诺日 |

## 9. 页面（3 个）

1. **需求看板** —— 10 列，列头 = 状态名 + 数字；卡片 = 标题 / 等谁 / 编号 + 停留天数；需要你动的卡加主色框。
2. **版本** —— 时间窗 + 甘特 + 进度（时间口径）。
3. **设置** —— 我的（改密码 / MCP 地址 / 令牌 / 通知偏好）+ 项目（工作流 / 成员与类型 / 通知规则）。
